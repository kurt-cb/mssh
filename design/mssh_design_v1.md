## §1  System overview

### §1.1  Defining property ✅

mssh is a runtime, CA-mediated SSH authorization system. SSH client
identity and credentials don't change; **authorization** moves out of
the client and into a CA on a separate, restricted network. The
server contacts the CA at connection time and gets a short-lived
authorization decision back.

**The defining property: a stolen client credential is useless if the
attacker can't reach the CA.** Put the CA on a network reachable
only from your SSH servers; stolen keys can't trigger authorization
from anywhere else.

**Threat model summary.** Three named threats motivate the design:

1. **Stolen client credential, attacker on the public Internet.** The
   attacker holds a valid mssh client cert + key (or a valid SSH
   user key) but is not on the CA's reachable network. The CA never
   sees the authorize request; msshd's authz cache holds no entry
   for the attacker; the connection is denied at the outer mTLS hop
   or at the CA-call hop. (Mitigated by §1.1 + §5.3.5 + §5.3.7's
   chain-pin to `auth_trust_root`.)

2. **Compromised msshd host.** The attacker has root on a single
   msshd. They can read the msshd-local user-CA key (§5.3.13) and
   mint ephemeral OpenSSH certs for the hermetic inner sshd, but
   they cannot mint *authz certs* (Root + intermediates are not
   on msshd) and cannot extend their reach to other msshd hosts.
   (Mitigated by §2.1 two-hierarchy separation.)

3. **Compromised CA host.** The attacker has root on mssh-ca. They
   can mint any authz cert and any bypass cert. Recovery is to
   rotate the Root and re-enroll. **No technical mitigation; the
   CA host is the trust anchor.** (Operational mitigation:
   network-restrict the CA per §1.1, future HSM/offline-root per
   §18.3.)

The system does **not** defend against:

- Network attacker who can reach both the client and the CA (e.g. an
  insider on the same VLAN). The defining property requires network
  separation.
- Compromise of the operator workstation that holds an `admin` or
  `superuser` mssh-admin cert.
- Side-channel attacks against TLS itself.

See §16.1 for the per-failure-mode behavior and §16.2 for recovery
paths.

### §1.3  Glossary ✅

Single source of truth for every domain noun. Authoritative — prose
elsewhere in the doc must match.

| Term | Meaning |
|------|---------|
| **authz cert** | Short-lived (minute-scale) X.509 cert minted by mssh-ca per `/v1/authorize` call. Signed by the `user-mint` intermediate. Carries principal + policy in custom OIDs (§14.5). Consumed by msshd's authz cache (§5.3.5). Never reaches the SSH layer. |
| **bypass cert** | X.509 cert minted offline by an mssh-ca superuser via `mssh-admin bypass-cert mint`. Signed by the `bypass-mint` intermediate. Carries the `OID_CA_BYPASS` marker (`1.3.6.1.4.1.55555.1.8`). Operator stores it offline; presents it via `mssh --inject-bypass-cert` when CA is unreachable. (§13.2) |
| **ephemeral OpenSSH cert** | Short-lived OpenSSH user cert signed by msshd's local user-CA (§5.3.13). Minted per-session; consumed by the hermetic inner sshd. Never seen by the mssh client. |
| **hermetic inner sshd** | OpenSSH subprocess owned by msshd, listening only on localhost, with a config msshd controls. Trusts only msshd's local user-CA. (§5.3.10 / §5.3.11) |
| **user-mint** | Intermediate CA that signs authz certs (one per `/v1/authorize` call). msshd pins to it via `auth_trust_root`. (§2.2) |
| **bypass-mint** | Intermediate CA that signs bypass certs. msshd pins to it via `bypass_trust_root` (separate from `auth_trust_root`). (§2.2) |
| **host-mint** | Intermediate CA that signs mTLS server certs for mssh-ca and msshd. (§2.2) |
| **auth** | Intermediate CA that signs mTLS client certs for mssh-admin operators and mssh users. (§2.2) |
| **external-\*** | Per-tenant intermediates minted via `mssh-admin intermediate mint-external`. CA stores only the public cert; external entity holds the key. Trust-excluded from the mssh validation paths. (§2.6, §15.3) |
| **outer mTLS** | The TLS 1.3 mutual-auth handshake between the mssh client and msshd. (§3.1) |
| **inner SSH** | The localhost SSH session between msshd and the hermetic inner sshd. (§3.4) |
| **session-RPC header** | The first typed frame on the outer mTLS tunnel, carrying `{"version", "user", "command"}`. (§14.7) |
| **authz cache** | msshd's per-principal store of recent authz decisions. Keyed by mTLS-identity → authz cert. Persists across restart at `<state_dir>/authz_cache.json`. Source-tagged (`ca` or `bypass`). (§5.3.5, §13.1) |
| **CRL** | Per-issuer, append-only, sequence-numbered revocation log. mssh-ca publishes; msshd consumes via piggyback on authorize responses + on-demand fetches. (§13.3, §4.3.5) |
| **strict-mode gate** | msshd's safety lever that refuses cache hits and forces live CA calls when the sum of per-issuer CRL gaps exceeds `crl_strict_threshold` (default 50). (§5.3.9) |
| **fallback / gated / enforce** | The three msshd operating modes. See §1.4. |
| **operator** | A human (or automation) holding an `admin` or `superuser` mssh-admin cert. Manages enrollment, policy, intermediates. |
| **principal** | The identity an `/v1/authorize` request is *about*. For SSH sessions this is `(user, host)` derived from the mssh client cert subject + the session-RPC `user` field. |
| **AKC** | OpenSSH `AuthorizedKeysCommand`. The integration point used by `akc_shim` to plug mssh-ca into an unmodified OpenSSH. (§9.3.4, §15.6) |
| **broker** | The mssh-passkey relay between an RP (mssh-ca or an external tool) and the user's browser. Holds no key material. (§8, §15.4) |
| **adhoc lab** | LXC-based reference deployment provisioned by `setup_adhoc.sh`. Defined in §17.1. |

### §1.4  Operating modes

`msshd` supports three modes selected at config time by the
`msshd.yaml` `mode:` field. The mode is the single most important
operator-visible choice in mssh — it determines the trust boundary
between mssh-ca and the operator's existing SSH posture.

| Mode | Outer auth (mssh→msshd) | Inner auth (msshd→sshd) | Whose policy wins | Status |
|---|---|---|---|---|
| **fallback** | none — TCP proxy | the operator's existing sshd_config | the operator | ✅ |
| **gated** | mTLS + CA approval | the operator's existing sshd_config | the operator, gated by CA | 🚧 P2 v1 blocker |
| **enforce** | mTLS + CA approval + ephemeral cert minted | hermetic minimal sshd_config | mssh-ca | ✅ |

The intended adoption journey is **fallback → gated → enforce**,
each step reversible by a single config flag (§13.8). Operators can
preserve their existing sshd policy as long as they want and flip
to CA-mediated auth on their own schedule.

#### §1.4.1  fallback mode ✅

Pure TCP proxy. msshd accepts a TCP connection on its outer port and
forwards bytes verbatim to the operator's existing sshd. No CA call,
no mTLS, no certificate inspection. Used during initial adoption to
verify the gateway is wired in correctly without changing
authentication semantics.

Configuration:

```yaml
mode: fallback
fallback:
  upstream_host: 127.0.0.1
  upstream_port: 22
```

#### §1.4.2  gated mode 🚧 P2 (v1 ship blocker)

mTLS + CA approval at the outer hop, but auth is delegated to the
operator's existing `/etc/ssh/sshd_config` at the inner hop. After a
successful CA authorize response, msshd opens a plain SSH tunnel to
the operator's sshd; the user's existing SSH key proves identity to
that sshd as it would have before mssh existed.

Use case: operators with years of accumulated sshd_config / PAM /
AllowGroups policy who want CA-mediated **access gating** before
moving to full CA-mediated **authentication**. The CA can deny a
connection without the operator having to migrate their auth
machinery.

Configuration:

```yaml
mode: gated
gated:
  upstream_host: 127.0.0.1
  upstream_port: 22
  ca: { ... }                  # same CA block as enforce mode
  outer_mtls: { ... }          # same outer-mTLS block as enforce mode
```

Estimated scope: ~300-500 LOC + ~20 tests (matrix: deny / allow /
mTLS-fail / CA-down / fallback-to-enforce-flip).

#### §1.4.3  enforce mode ✅

mTLS + CA approval + ephemeral OpenSSH cert mint + hermetic inner
sshd. mssh-ca is the authoritative policy point; the operator's
`/etc/ssh/sshd_config` is bypassed entirely (the hermetic inner
sshd does not Include it and runs on localhost).

This is the mode v1 ships as the recommended production posture.

Configuration:

```yaml
mode: enforce
ca: { ... }
outer_mtls: { ... }
inner:
  mode: long_lived            # or per_connection
  ...
```

#### §1.4.4  Mode-selector semantics ✅

- The `mode:` field is read at msshd startup. Changing it requires
  a restart.
- Flipping between modes is **reversible by config edit**. No state
  needs to migrate between modes; each mode is self-contained.
- Each mode declares its own required config block (`fallback:`,
  `gated:`, or `outer_mtls:` + `inner:`). msshd refuses to start
  if the required block for the selected mode is absent or
  malformed (§13.9.7 default-deny on missing config).
- Multiple msshd instances on the same host running in different
  modes is supported as long as they listen on different ports
  (e.g. a fallback msshd on :22 + an enforce msshd on :2200 during
  staged migration).

## §2  Trust model + PKI hierarchy ✅

Everything cryptographic that crosses a module boundary. The
load-bearing rules live here.

### §2.1  Two-hierarchy rationale ✅

mssh uses **two** root-of-trust hierarchies, deliberately kept
separate:

- **CA signing hierarchy** (`Root + 4 intermediates`, §2.2).
  Issues the X.509 authorization certs that msshd consumes, plus the
  mTLS certs for enrolled servers, admins, and users. Lives entirely
  on the mssh-ca host. The high-value secret.
- **User-facing hierarchy.** Could be the CA signing hierarchy
  itself (a self-contained deployment uses mssh-ca for everything),
  or a separate web-PKI / corporate CA (the operator picks).
  Operationally rotatable independent of authz.

Separate because they answer different questions: the CA signing
hierarchy answers *"is this principal authorized for this action
right now?"*; the user-facing hierarchy answers *"is the network
identity on the other end of the TLS handshake who they claim to be?"*

A third, internal hierarchy lives inside each msshd:

- **msshd's local user-CA** (§5.3.13). Mints ephemeral OpenSSH
  user certs for the hermetic inner sshd (§5.3.10 / §5.3.11).
  Never leaves the msshd host. Rotation is cheap — generate a
  new pair, restart msshd, the inner sshd re-loads
  `TrustedUserCAKeys`.

The three hierarchies never co-sign. A cert minted by one cannot be
chain-validated by a validator pointed at another. This is what §2.3
makes a hard rule.

### §2.2  Root + named intermediates ✅

```
root (mssh-root, self-signed, long-lived ~20 years)
 ├── user-mint    — per-session authz certs (the hot path)
 ├── bypass-mint  — operator-presentable CA-bypass authz certs
 ├── host-mint    — server identities (CA TLS, msshd mTLS-to-CA)
 ├── auth         — admin / user mTLS client certs
 └── external-<name>  (optional, multiple; §2.6)
```

Why these four specifically:

- **user-mint** — the hot path. Signs every `/v1/authorize`
  response. Compromise lets an attacker mint live grants —
  rotation is sensitive but routine.
- **bypass-mint** — the cold-path "operator break-glass" key.
  Signs pre-issued bypass certs that are stored offline. Compromise
  lets an attacker mint a cert that bypasses live CA control. The
  highest-value key after Root. Rotation is rare; custody is
  strictest.
- **host-mint** — signs server identities (mssh-ca's own TLS cert
  + each msshd's mTLS-to-CA client cert). Compromise allows server
  impersonation but does not directly mint authz.
- **auth** — signs admin / user mTLS client certs. Compromise
  allows a user impersonation but does not mint authz directly.

**Issuer identifier format.** `<short-name>:<pubkey-fp16>` — short
name for human readability in logs, pubkey fingerprint (first 16
hex of SHA256 over SPKI) for cryptographic stability. Survives
renames; differs across rotations.

Examples:
- `user-mint:7f3c4b2a8d1e5f60`
- `bypass-mint:a1b2c3d4e5f60718`

**On-disk layout** (post-`mssh-ca bootstrap`):

```
<ca_dir>/
  root-cert.pem
  root-key.pem                    (mode 0600)
  intermediates/
    user-mint/
      cert.pem
      key.pem                     (mode 0600)
    bypass-mint/{cert.pem, key.pem}
    host-mint/{cert.pem, key.pem}
    auth/{cert.pem, key.pem}
    external-<name>/cert.pem      (cert only; key handed off OOB)
  crl/
    user-mint.jsonl               (per-issuer append-only)
    bypass-mint.jsonl
    host-mint.jsonl
    auth.jsonl
  tls-server-cert.pem             (leaf + host-mint chain bundle)
  tls-server-key.pem              (mode 0600)
  bootstrap-admin-cert.pem        (leaf + auth chain bundle)
  bootstrap-admin-key.pem         (mode 0600)
  enrollment.yaml
  audit.jsonl
```

Leaf PEM files are **chain bundles** (leaf + intermediate
concatenated). The Root is the trust anchor; validators only need
`root-cert.pem` to walk a chain — but per §2.3 they must additionally
pin to a specific intermediate.

Internal intermediates carry `path_length=0` (sign leaves only).
External intermediates (§2.6) carry operator-chosen `path_length`.

### §2.3  Validation pinning rule (LOAD-BEARING) ✅

**Every mssh validator pins to a specific intermediate, never to
the Root.**

Concrete trust-store contents per role:

| Validator | Pinned intermediate |
|-----------|---------------------|
| msshd, validating incoming user mTLS handshake | **auth** |
| msshd, validating authz cert in `/v1/authorize` response | **user-mint** |
| msshd, validating bypass cert at injection | **bypass-mint** |
| mssh, validating msshd's TLS server cert | **host-mint** |
| mssh-admin, validating mssh-ca's TLS server cert | **host-mint** |

Configuration surface in `msshd.yaml`:

```yaml
ca:
  auth_trust_root:   /etc/mssh/intermediates/user-mint/cert.pem
  bypass_trust_root: /etc/mssh/intermediates/bypass-mint/cert.pem
```

The trust-store file is the **specific intermediate cert** — not
the Root, not a bundle that includes the Root. Chain validation
walks `leaf → intermediate (must equal pinned) → Root`. If the
chain doesn't terminate at the pinned intermediate, validation
fails — even if the chain validates to the Root through a
different intermediate.

**Why this rule is load-bearing.** mssh-ca mints leaves under
multiple intermediates simultaneously: an `auth`-signed admin cert,
a `user-mint`-signed authz cert, and (per §13.7 / §15.2) a
`host-mint`- or auxiliary-signed X.509 leaf for a non-mssh
application all share the same Root. Without intermediate pinning,
a validator that accepts "chain → Root" accepts any of them. An
attacker who can convince mssh-ca to issue a generic TLS server
leaf (a low-privilege operation) could then present that leaf as
a user mTLS handshake to msshd (a high-privilege operation), and
msshd would accept. The intermediate is the specificity boundary
that closes this attack.

This is standard X.509 — `cryptography`'s `verify_certificate` and
OpenSSL's `X509_STORE_CTX_init` with the pinned intermediate as
the trust anchor both do the right thing. The discipline is in
**never putting the Root cert alone in a trust store**; always pin
the intermediate.

Verification: `python/tests/test_pki_v023_pinning.py` exercises
the pinning behavior for every validator in the table above
(Tests: §2.3).

### §2.4  Cert profiles + custom OIDs ✅

Every mssh cert type carries a cert-profile-specific Extended Key
Usage (EKU) and one or more **custom critical extensions** so that
a validator can refuse a cert that *would* chain-validate but is
the wrong type. Full extension/OID table in §14.5; this section
summarizes which OIDs appear on which cert type.

| Cert type | Signed by | Key markers | EKU |
|-----------|-----------|-------------|-----|
| Authz cert | `user-mint` | `OID_AUTHZ_PRINCIPAL`, `OID_AUTHZ_VALID_FROM`, `OID_AUTHZ_VALID_TO` | id-kp-clientAuth |
| Bypass cert | `bypass-mint` | `OID_AUTHZ_PRINCIPAL` + **critical** `OID_CA_BYPASS` (`1.3.6.1.4.1.55555.1.8`) | id-kp-clientAuth |
| mTLS server cert (mssh-ca / msshd) | `host-mint` | (none mssh-specific) | id-kp-serverAuth + id-kp-clientAuth |
| mTLS user cert (mssh) | `auth` | `OID_USER_NAME` | id-kp-clientAuth |
| mTLS admin cert (mssh-admin) | `auth` | `OID_USER_NAME`, `OID_ADMIN_ROLE` | id-kp-clientAuth |
| Ephemeral OpenSSH user cert | msshd-local user-CA | OpenSSH cert format (not X.509) | n/a |
| Auxiliary X.509 leaf (§13.7) | `host-mint` or operator-chosen | none | per leaf type |

**§13.9.8 (cert OID + marker enforcement)** requires that every
validating site check the markers explicitly, not infer the cert
type from where it appeared. A validator that accepted any
`auth`-signed cert as an admin cert without checking for
`OID_ADMIN_ROLE` would conflate user certs and admin certs.

### §2.5  Rotation + revocation semantics ✅

Two mechanisms, complementary:

**Rotation (intermediate-level).** `mssh-admin intermediate rotate
<role>` generates a new keypair for one intermediate, signs the
new intermediate cert under Root, and updates the on-disk layout.
The old intermediate's keypair is archived with a timestamp suffix
(`intermediates/<role>/key.pem.archived-2026-05-22`) so existing
unexpired leaves under it remain verifiable until they naturally
expire. New leaves are signed by the new keypair.

Effect on outstanding leaves: a rotation creates a new `issuer_id`
(`<role>:<new-fp16>`). Outstanding leaves still chain through the
old intermediate, which is still signed by Root — they continue to
validate. Validators that pin to the role by *file path* (the
common case) see the rotation when they next read the cert file;
validators that pin to the file by *fingerprint* (paranoid mode)
must be updated when the intermediate rotates.

**Revocation (leaf-level), per-issuer CRL.** Each intermediate
owns an append-only `crl.jsonl`:

```
<ca_dir>/crl/<role>.jsonl
```

Each entry: `{seq, revoked_at, serials, revoked_by, reason}`.
Sequence numbers are forever-incrementing within an issuer.

Wire propagation: the `/v1/authorize` response carries
`current_crl_seqs: {issuer_id: seq, ...}`. msshd persists its
`last_applied_seqs` per issuer; when `current > last` for any
issuer, msshd fetches the missing entries via
`GET /v1/crl?issuer=<id>&after=N&limit=K` and applies them to its
authz cache (invalidate-by-serial). Strict-mode gate (§5.3.9)
forces live CA calls when the gap grows too large.

**Cross-issuer revocations don't cross-pollinate.** A revocation
against a `user-mint`-issued cert does not appear in
`bypass-mint`'s CRL — they're separate logs. This is what makes
"compromise one intermediate, rotate just that one" tractable.

### §2.6  External Intermediate CA tier ✅

`mssh-admin intermediate mint-external --name <X> --path-length N`
mints a CA cert signed by the Root, hands the *private key* to the
external entity (one-shot, out-of-band) and stores **only the
public cert** on the mssh-ca host. The external entity is then
free to mint whatever leaves they want under that CA.

Differences from the four internal intermediates:

1. **path_length** — operator-chosen at mint time. Typically `1`
   (external can run a one-deep sub-CA) or `0` (external mints
   leaves only).
2. **Subject marking** — carries `Organization=<entity name>` and
   `OrganizationalUnit=external`. Audit log records the mint with
   the external-X serial.
3. **Trust-store exclusion** — **no** mssh validator carries
   `external-<name>` in its trust store. A leaf chaining through
   external-X terminates chain validation without a trust anchor
   under §2.3, and is refused.

Why this is a useful integration point (§15.3): the operator can
delegate cert-issuance authority to a partner organization without
giving them any influence over mssh's auth decisions. The partner's
certs are real X.509 certs that validate under their own
infrastructure (e.g. an internal HTTPS deployment); mssh actively
refuses to accept those certs for any mssh purpose.

Misuse handling: if the external entity issues unexpected leaves,
revoke the external-X cert itself via the standard CRL flow. The
mssh Root remains uncompromised. The external entity's leaves are
chained through external-X → Root, but Root is not in any mssh
trust store, so the revocation is the operator's signal to other
relying parties (whoever *did* trust external-X) — mssh itself
never had a problem.

Verification: `python/tests/test_external_intermediate.py`
exercises the trust-exclusion property — an external-X-signed
leaf presented to msshd's `auth_trust_root` (pinned to `user-mint`
or `auth`) is refused (Tests: §2.6).

## §3  Wire protocols ✅

Every byte-stream contract between components. This chapter
describes the **shape** of each protocol; exhaustive schemas
(byte-by-byte, field-by-field) live in §14.

### §3.1  mssh ↔ msshd outer protocol ✅

```
mssh client                                          msshd
   │                                                    │
   │── TLS 1.3 ClientHello + ClientCert (auth-mTLS) ──▶ │
   │◀── TLS 1.3 ServerHello + ServerCert (host-mint) ── │
   │── TLS finished ────────────────────────────────▶ │
   │   {tunnel established; outer mTLS proven both ways}│
   │                                                    │
   │── JSON header line ──────────────────────────────▶ │
   │   {"v": 1, "user": "alice", "command": [...],     │
   │    "interactive": false, "supports_framing": true} │
   │                                                    │
   │◀── JSON ack ───────────────────────────────────── │
   │   {"v": 1, "ok": true, "framing": true}            │
   │                                                    │
   │── typed framing protocol v1.1 ◀──────────────────▶ │
   │   (STDIN/STDOUT/STDERR/BANNER/EXIT/DENY/...        │
   │    frames; full schema in §14.7)                   │
   │                                                    │
```

Three layers:

1. **TLS 1.3 + mTLS.** mssh client presents an `auth`-signed mTLS
   client cert (§2.3). msshd presents a `host-mint`-signed mTLS
   server cert. Cipher suites: TLS_AES_128_GCM_SHA256,
   TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256.
   Renegotiation and 0-RTT are disabled. SNI carries the msshd
   service name.

2. **JSON session-RPC header + ack.** Single-line JSON pre-stream.
   Header carries `{v, user, command, interactive,
   supports_framing}`. Ack carries `{v, ok, framing, reason?}`.
   This is the only place msshd knows what user the connection
   is for — the mTLS cert proves *who* the operator is, the
   header `user` field says *which principal they're claiming
   to act as* (relevant when one identity has access to many
   principals).

3. **Typed framing protocol v1.1.** After ack, both sides switch
   to framed mode if both opted in. Each frame has a fixed 8-byte
   header `(type:u8, flags:u8, reserved:u16, length:u32)` followed
   by `length` bytes of payload. Frame types include STDIN,
   STDIN_EOF, WINSIZE, STDOUT, STDERR, BANNER, EXIT, SIGNAL, DENY,
   CLOSE. Full schema in §14.7.

**Bypass-cert injection variant.** When the client passes
`--inject-bypass-cert`, the JSON header carries an extra field
`bypass_cert: "<base64 PEM>"`. msshd validates per §13.2,
writes the cert into the authz cache, acks, and closes the
connection (no session opened). Detailed in §5.3.7.

**Backward compat.** Negotiation is additive — both sides MAY
advertise `supports_framing: true` / `framing: true`. If either
omits, both fall back to raw byte pump (v1.0). v1 of mssh ships
with framing on; v1.1 is the v1-frozen protocol.

### §3.2  msshd ↔ mssh-ca ✅

```
msshd                                              mssh-ca
  │                                                    │
  │── TLS 1.3 ClientHello + ClientCert (host-mint) ──▶ │
  │◀── TLS 1.3 ServerHello + ServerCert (host-mint) ── │
  │                                                    │
  │── POST /v1/authorize ─────────────────────────────▶ │
  │   {version, request_id, server_id, client{...},   │
  │    connection{...}, issued_at, last_crl_seqs:{...},│
  │    protocol_version, inner_sshd_kind, ...}        │
  │                                                    │
  │◀── 200 OK ──────────────────────────────────────── │
  │   {result:"granted", credentials:{cert_pem,...},   │
  │    current_crl_seqs:{user-mint:42,...},            │
  │    inner_sshd_config?, envelope-fields...}         │
  │                                                    │
  │   ── OR ──                                          │
  │                                                    │
  │◀── 403 Forbidden ───────────────────────────────── │
  │   {result:"denied", denied_reason:"...", ...}      │
  │                                                    │
  │── GET /v1/crl?issuer=<id>&after=N&limit=K ────────▶ │
  │   (when last_applied_seqs[id] < current_crl_seqs[id])│
  │                                                    │
  │◀── 200 OK ──────────────────────────────────────── │
  │   {current_seq, entries:[{seq,serials,reason,...}]} │
  │                                                    │
  │── POST /v1/cert/renew ────────────────────────────▶ │
  │   (when msshd's own mTLS cert is in renew window)   │
  │                                                    │
```

HTTPS + mTLS at all times. msshd's client cert is `host-mint`-signed
(its mTLS-to-CA identity); mssh-ca's server cert is also
`host-mint`-signed.

Endpoint set msshd uses:
- `POST /v1/authorize` — per-incoming-connection (§4.3.1).
- `GET  /v1/crl` — CRL sync (§5.3.8).
- `GET  /v1/crl.pem` — operator-readable CRL (rarely called).
- `POST /v1/cert/renew` — daily systemd timer (§13.4).

Full endpoint catalog with exhaustive request/response schemas in
§14.1.

**Sequence-number semantics.** `last_crl_seqs` is a map keyed by
issuer_id (`<short-name>:<pubkey-fp16>`). The CA's response always
includes `current_crl_seqs` listing every issuer it knows about.
msshd compares per-issuer; for any issuer where `current > last`,
msshd fetches the missing entries asynchronously (off the
authorize hot path).

### §3.3  mssh-admin ↔ mssh-ca ✅

```
mssh-admin                                         mssh-ca
   │                                                  │
   │── TLS 1.3 + mTLS (auth-signed client cert) ────▶ │
   │                                                  │
   │── POST /v1/admin/<verb> ────────────────────────▶ │
   │                                                  │
   │  ── happy path ──                                 │
   │◀── 200 OK + JSON envelope ─────────────────────── │
   │                                                  │
   │  ── 2FA-gated path (§13.5) ──                     │
   │◀── 202 Accepted ────────────────────────────────── │
   │   {ceremony_id, approval_url, poll_url, ttl_s}    │
   │                                                  │
   │   ... operator taps phone ...                     │
   │                                                  │
   │── GET /v1/admin/passkey/ceremony/<id> ───────────▶ │
   │◀── 200 OK {status: "approved"} ──────────────── │
   │                                                  │
   │── POST /v1/admin/<verb> (retry) ──────────────▶ │
   │◀── 200 OK ──────────────────────────────────── │
   │                                                  │
```

HTTPS + mTLS. mssh-admin presents an `auth`-signed admin mTLS
cert. mssh-ca derives the role (`superuser` / `admin` / `auditor`)
from the cert subject matched against the enrollment record. Every
admin call is audit-logged with the actor's subject + the action.

**202-Accepted 2FA pattern (§13.5).** When the policy requires
2FA, a mutating admin call returns 202 with a ceremony id +
approval URL. The CLI prints the URL (with terminal QR rendering
in v0.3.2+), the operator approves on a registered authenticator,
the CLI polls the ceremony endpoint, and on approval retries the
original call. The retry succeeds because the CA has now cached
the per-admin 2FA window. Detailed in §7.3.2 + §13.5.

Endpoints: `/v1/admin/*` for the full admin surface; `/v1/admin/
passkey/*` for ceremony polling; `/v1/admin/audit` for the audit
log query. Full catalog in §14.1.2.

### §3.4  msshd ↔ hermetic inner sshd ✅

Standard SSH protocol over localhost only. msshd is the SSH
*client* against its own inner sshd, presenting an ephemeral
OpenSSH user cert minted by msshd's local user-CA (§5.3.13).

```
msshd                                           inner sshd
  │                                                  │
  │   {prior to first connection:                     │
  │    msshd has spawned `sshd -f <hermetic.conf>`,    │
  │    inner sshd listens on 127.0.0.1:<port>}         │
  │                                                  │
  │── SSH-2.0 transport handshake ──────────────────▶ │
  │◀── SSH-2.0 transport handshake ─────────────────── │
  │                                                  │
  │── pubkey auth (ephemeral OpenSSH user cert) ────▶ │
  │◀── auth success ──────────────────────────────── │
  │                                                  │
  │   {channel: session, exec, pty, etc.}              │
  │                                                  │
```

Hermetic config invariants (full list in §5.3.10):

- `ListenAddress 127.0.0.1` — localhost only.
- `HostKey <local>` — msshd-generated, regenerated at restart.
- `TrustedUserCAKeys <local>` — pinned to msshd's local user-CA
  pubkey. **No other auth path.**
- No `PAM`, no `Include`, no `Match`.
- AEAD ciphers only; ed25519 + ecdsa-p256 host keys only.
- Logs to msshd's stderr (no syslog, no separate log files).

The cert presented by msshd carries the principal name + any
per-session `ForceCommand` / `SetEnv` policy as OpenSSH cert
critical-options. Hermetic sshd enforces these via stock OpenSSH
mechanisms — no application-layer policy translator on msshd.

### §3.5  External-tool ↔ mssh-ca ✅

A 3rd party tool acting as a WebAuthn RP for its own users, using
mssh-ca's passkey infrastructure. The integration point for
§15.5.

```
3rd-party tool                                      mssh-ca
     │                                                 │
     │── TLS 1.3 + mTLS (tool-cert) ─────────────────▶ │
     │                                                 │
     │── POST /v1/external/passkey/challenge ────────▶ │
     │   {user_handle, outcome_url, ttl_s}             │
     │                                                 │
     │◀── 200 OK ─────────────────────────────────── │
     │   {ceremony_id, approval_url, ttl_s}            │
     │                                                 │
     │   ... user taps phone via approval_url ...       │
     │                                                 │
     │◀── POST <outcome_url> ────────────────────────── │
     │   {ceremony_id, status: "approved"}              │
     │   (delivered by mssh-ca's two-hop callback path) │
     │                                                 │
     │── GET /v1/external/passkey/ceremony/<id> ──────▶ │
     │◀── {status: "approved", ...} ───────────────── │
```

Tool-mTLS endpoints under `/v1/external/passkey/*`. Each tool
registered via `mssh-admin external-tool add` receives a
tool-specific mTLS client cert and an `outcome_url_prefix`
constraint. Frozen contract details:

- **Cross-tool isolation.** Tool A's mTLS cert cannot read Tool
  B's ceremonies — the CA matches the cert's tool-id to the
  ceremony's owning tool.
- **outcome_url_prefix.** When tool registers, it declares a
  URL prefix; outcome callbacks are only delivered to URLs
  matching that prefix. Prevents a compromised tool cert from
  redirecting outcomes to attacker-controlled URLs.
- **AAGUID allowlist.** v1 inherits the CA-global allowlist;
  per-tool override is post-v1.

Detailed in §13.6 (cross-cutting flow) + §14.1.3 (endpoint
schemas).

### §3.6  Broker ↔ mssh-ca / Broker ↔ browser ✅

mssh-passkey is a relay between an RP (mssh-ca, an external tool)
and the user's browser. Two listeners:

```
              ┌─────────────────────────────────────┐
              │           mssh-passkey               │
              │           (broker module)            │
              │                                      │
HTTPS public  │      ┌─────────────┐                 │
browser ──────┼──────▶  /register/<id>               │
              │      │  /approve/<id>                │
              │      └─────────────┘                 │
              │                                      │
mTLS backend  │      ┌─────────────┐                 │
(mssh-ca ─────┼──────▶  /broker/ceremony[/<id>]       │
or tool)      │      │  GET / POST / DELETE          │
              │      └─────────────┘                 │
              │                                      │
              │  ┌─────────────────────────────────┐ │
              │  │  callback worker (outbound mTLS)│ │
              │  │  back to RP's outcome_url       │ │
              │  └─────────────────────────────────┘ │
              └─────────────────────────────────────┘
```

**Front-end public side (HTTPS, no mTLS).** Browser hits
`/register/<id>` or `/approve/<id>`; broker serves a Bootstrap5
page with a vanilla-JS WebAuthn driver. TLS terminated at apache2
in production or in-process in `front_end: dev` mode.

**Back-end mTLS side.** mssh-ca (acting as RP) calls
`POST /broker/ceremony` to start a ceremony, polls
`GET /broker/ceremony/<id>`, or `DELETE`s to cancel. Authenticated
by mTLS — apache2 forwards the client CN via `X-Client-CN`; the
broker matches against a registered RP allow-list.

**Callback delivery.** When a ceremony completes (approved /
denied / expired), the broker queues an outbound mTLS POST back
to the RP's `outcome_url`. Retry schedule: immediate, +5s, +30s,
+2m, +10m.

**No key material.** The broker has no per-user state and holds
no keys. The browser-side WebAuthn credential is bound to the RP
ID (the RP's domain), not the broker's. The broker stores only
ceremony records (per §14.6 SQLite schema).

Frozen contract: §15.4 makes this the wire protocol a 3rd party
broker would implement to swap out mssh-passkey.

## §4  Module: mssh-ca ✅

The central authorization service. Flask + mTLS. Mandatory in every
v1 deployment.

### §4.1  Purpose ✅

mssh-ca is the **single trust authority** for an mssh deployment. Four responsibilities:

1. **Authorize** — evaluate per-connection authorization requests
   from enrolled msshds, mint short-lived X.509 authz certs.
2. **Enroll** — maintain the inventory of servers, users, keys,
   policies, admins, external tools, intermediate CAs.
3. **Mint** — issue every cert mssh needs (authz, bypass, mTLS
   server/client, ephemeral, auxiliary §13.7) under the Root +
   intermediates hierarchy (§2.2).
4. **Audit** — append every authorize decision and every admin
   action to a tamper-evident JSON-Lines log (§4.3.7, §13.9.6).

The CA signing keys (Root + 4 intermediates) never leave the CA
host. The CA is typically deployed on a private network reachable
only from enrolled msshds and from operator workstations running
mssh-admin.

### §4.2  Interconnections ✅

| Direction | Other party | Wire | Endpoints |
|-----------|------------|------|-----------|
| Inbound | msshd | mTLS HTTPS (§3.2) | `/v1/authorize`, `/v1/crl`, `/v1/crl.pem`, `/v1/cert/renew` |
| Inbound | mssh-admin | mTLS HTTPS (§3.3) | `/v1/admin/*` |
| Inbound | external tool | mTLS HTTPS (§3.5) | `/v1/external/passkey/*` |
| Inbound | mssh-admin-web | mTLS HTTPS (§3.3) | `/v1/admin/*` read-only subset |
| Inbound | mssh-mcp | mTLS HTTPS (§3.3) | `/v1/admin/*` read-only subset (§12) |
| Outbound | mssh-passkey broker | mTLS HTTPS (§3.6) | broker ceremony API |
| Outbound | external tool | mTLS HTTPS (§3.5) | tool's `outcome_url` (callback) |

The CA does **not** call msshd. The relationship is strictly
msshd→CA for authorize and CRL fetches; msshd holds no admin
authority.

### §4.3  Implementation

#### §4.3.1  Authorize handler ✅

`POST /v1/authorize` is the per-incoming-connection endpoint. Code:
`packages/mssh-ca/src/mssh/ca/authorize.py`.

Flow:

```
1. mTLS handshake — caller's cert must chain to host-mint and
   match an enrolled server's mtls_subject. Otherwise 401
   unknown_server.

2. Parse request body (§14.1.1 schema). Required fields:
   identity {type, data}, connection {source_ip, source_port,
   timestamp}. Optional: requested_channels, protocol_version,
   inner_sshd_kind/version, msshd_version, last_crl_seqs.

3. Clock-skew check — abs(connection.timestamp − ca_clock) >
   drift_window → 403 clock_drift.

4. Identity lookup — hash the identity blob, match against
   enrollment. Miss → 403 unknown_identity.

5. Policy match — §4.3.3 evaluates every policy attached to the
   matched identity against the connection context. No match →
   403 policy_mismatch.

6. 2FA enforcement (if policy requires) — §4.3.8 returns either
   "satisfied from cache", "challenge issued (202)", or
   "failed (403)".

7. Cert mint — §4.3.4 mints an authz cert signed by user-mint
   with the matched policy's principals + critical options.

8. Response envelope — embed cert, current_crl_seqs (§4.3.5),
   policy_summary, optional inner_sshd_config (§4.3.12).

9. Audit write — §4.3.7 logs the decision (granted or denied)
   with request_id, actor, target, detail.
```

Deny reasons (stable enum, callers may switch on these):
`unknown_server`, `bad_request`, `clock_drift`,
`invalid_identity_cert`, `unknown_identity`, `policy_mismatch`,
`source_denied`, `time_window`. Detail goes to audit, not the
wire (§4.3.7 timing-side-channel posture).

#### §4.3.2  Enrollment store ✅

On-disk persistence at `<ca_dir>/enrollment.yaml` (v1) or a
SQLite back-store in production deployments (the on-disk schema
is the abstraction the admin API operates on).

Top-level keys:
- `servers` — `{name: {mtls_subject, groups, enrolled_at,
  enrolled_by}}`.
- `users` — `{username: {enrolled_at, enrolled_by, keys[],
  policies[], passkey_credentials[]}}`.
- `admins` — `{name: {role, mtls_subject, enrolled_at,
  enrolled_by}}`. Role is one of `superuser`, `server-admin`,
  `user-admin`, `auditor`.
- `external_tools` — `{tool_id: {mtls_subject,
  outcome_url_prefix, aaguid_allowlist?, enrolled_at,
  enrolled_by}}`.
- `intermediates` — `{role: {cert_path, key_path?, fp16,
  rotated_at?}}` for each of `user-mint`, `bypass-mint`,
  `host-mint`, `auth`, and each `external-<name>`.
- `templates` — per-server / per-group / fleet-default inner-sshd
  config overrides (§4.3.12).

Atomic writes: every admin handler that mutates state writes
`enrollment.yaml.tmp` → fsync → rename. Concurrent reads are
cheap; writes serialize on a process-wide lock.

Full schema in §14.4.

#### §4.3.3  Policy engine ✅

A policy attached to a user is a set of constraints. The engine
evaluates each constraint against the connection context.

Policy schema:
```yaml
- servers:       ["srv-acct-01"]           # explicit names; OR
  server_groups: ["accounting"]             # group-matched
  channels:      ["session", "direct-tcpip"]
  source_cidrs:  ["10.0.0.0/8"]
  time_window:   {after: "08:00Z", before: "18:00Z"}
  max_cert_validity_seconds: 600
  force_command: "/usr/bin/safe-shell"      # optional
  environment:   {KEY: VALUE}               # optional
  require_2fa:   passkey                    # optional
  twofa_within_seconds: 3600                # required if require_2fa set
```

Evaluation rules:
- `servers` ∪ `server_groups` — the union of explicit + group
  match. Empty = no constraint.
- `channels` — the request's `requested_channels` must be a
  subset.
- `source_cidrs` — the request's `connection.source_ip` must lie
  in the intersection of all matching policies' CIDRs.
- `time_window` — request `connection.timestamp` must fall inside
  every matching policy's window (intersection).
- `max_cert_validity_seconds` — the cert's `not_after` is capped
  by the minimum of all matching policies.
- `force_command` + `environment` — applied as OpenSSH cert
  critical-options on the minted cert.
- `require_2fa` — gates the call through §4.3.8.

If no policy matches, the result is deny. There is no "default
allow".

#### §4.3.4  Cert minter ✅

Single module (`cert_minter.py`) that mints every cert type. Per
§2.4, every cert type has a distinct profile (EKU + custom
markers).

Cert-mint operations:

| Operation | Intermediate | Validity | Caller |
|-----------|--------------|----------|--------|
| Mint authz cert | `user-mint` | per-policy (seconds–minutes) | §4.3.1 |
| Mint bypass cert | `bypass-mint` | per-request (days–months) | §4.3.6 superuser only |
| Mint server mTLS cert | `host-mint` | months–years | §4.3.6 `server.add` |
| Mint admin mTLS cert | `auth` | years | §4.3.6 `admin.add` |
| Mint user mTLS cert | `auth` | months–years | §4.3.6 `user.key.add` (if x509) |
| Mint auxiliary leaf (§13.7) | `host-mint` (TLS) or operator-chosen | per-cert | §4.3.6 `cert mint`, `openvpn issue`, `wireguard ...` |
| Sign external intermediate | Root | years | §4.3.6 `intermediate mint-external` |
| Sign rotated intermediate | Root | years | §4.3.6 `intermediate rotate` |

Cert profiles enforce per §2.4. The minter refuses to issue a
cert whose markers don't match the cert's intended type — e.g.
it refuses to issue an `auth`-signed leaf without `OID_USER_NAME`
populated.

Serial generation: cryptographically random 20-byte integer.
The CA records every issued serial in audit so a future
revocation can be tied back to the issuing event.

#### §4.3.5  CRL registry ✅

Per-issuer, append-only revocation log. Code: `crl.py`.

Layout:
```
<ca_dir>/crl/
  user-mint.jsonl
  bypass-mint.jsonl
  host-mint.jsonl
  auth.jsonl
  external-<name>.jsonl  (if external intermediate exists)
```

Each line: `{seq, revoked_at, serials, revoked_by, reason}`.
Sequence is monotonic within an issuer.

`CRLRegistry` wraps the per-issuer `CRLStore`s. Operations:

- `register(issuer_id, serial, reason, actor)` — append.
- `current_seq(issuer_id) → int` — for authorize-response
  piggyback.
- `entries_after(issuer_id, after_seq, limit) → list` — for
  msshd's CRL sync.
- `is_revoked(issuer_id, serial) → bool` — internal sanity check.

Endpoints:
- `POST /v1/admin/cert/revoke` — superuser-only; CA auto-detects
  the issuer from the serial or accepts an explicit `issuer`
  field.
- `GET /v1/admin/crl?issuer=<id>&after=N&limit=K` — admin or
  auditor view.
- `GET /v1/crl?issuer=<id>&after=N&limit=K` — msshd-facing
  (same RBAC as `/v1/authorize`).
- `GET /v1/crl.pem?issuer=<id>` — PEM-format CRL (operator
  convenience; used rarely).

#### §4.3.6  Admin handlers ✅

`/v1/admin/*` is the full operator surface. Each handler:

1. Verifies the caller's mTLS cert subject matches an enrolled
   admin record.
2. Checks role-vs-action via the matrix below.
3. (If applicable) gates through §4.3.8 2FA.
4. Performs the action.
5. Audit-logs the actor + action + outcome.

Roles (§14.1.2 has full action mapping):

| Role | Permissions |
|------|-------------|
| `superuser` | every action |
| `server-admin` | `server.*`, `template.set/unset/list/show`, `user.list`, `audit.read` |
| `user-admin` | `user.*`, `policy.*`, `server.list`, `audit.read`, `template.list/show` |
| `auditor` | every `*.list` + `audit.read` + `template.list/show` |

Endpoint set summary (full schemas in §14.1.2):

```
/v1/admin/server/add, /<n>, /<n>/groups, /list
/v1/admin/user/add, /<n>, /<n>/key, /<n>/key/<fp>, /list
/v1/admin/policy/add, /<id>
/v1/admin/admin/add, /<n>, /list
/v1/admin/cert/revoke
/v1/admin/crl
/v1/admin/bypass-cert/mint
/v1/admin/intermediate/list, /rotate, /mint-external
/v1/admin/external-tool/add, /<id>, /list
/v1/admin/audit
/v1/admin/template/set, /unset, /list, /effective/<server>
/v1/admin/passkey/<begin|complete|ceremony>
/v1/admin/openvpn/issue
/v1/admin/wireguard/...
```

#### §4.3.7  Audit log ✅

Append-only JSON-Lines at `<ca_dir>/audit.jsonl`. Every authorize
decision + every admin action.

Schema (§14.6):
```json
{
  "ts": "<ISO-8601 UTC>",
  "request_id": "<correlation-id>",
  "actor": "alice" | "admin:bob" | "external-tool:tool-id" | "ca:internal",
  "action": "authorize" | "server.add" | "policy.delete" | "intermediate.rotate" | ...,
  "target": "srv-acct-01",
  "result": "granted" | "denied" | "ok" | "error",
  "detail": { ... action-specific ... },
  "origin": "mssh-admin" | "mssh-admin-web" | "mcp" | "external-tool" | "msshd"
}
```

The `origin` field tags MCP-initiated calls (§13.9.2) and
external-tool-initiated calls so a security review can filter on
them.

**Timing-side-channel posture.** The CA's response time to
"denied" must not leak whether the user is enrolled (denied by
policy) vs. not enrolled (`unknown_identity`). Constant-work
denial paths are the v1 target; detailed deny reasoning goes
only to audit.

**§13.9.6 hardening.** v1 adds a hash-chain or signed-checkpoint
integrity story to the audit log: a periodic signed checkpoint
references the previous checkpoint's hash + the current log
position, so post-incident analysis can detect log truncation.
Retention + rotation policy is operator-configurable.

#### §4.3.8  Passkey RP — admin-2FA flow ✅

mssh-ca acts as the WebAuthn RP for its own admins. The
end-to-end story is §13.5; this section covers the CA's side.

Code: `passkey.py` (RP adapter), `passkey_broker.py` (broker
mTLS client), `admin.py` (the gated handlers).

Per-policy `require_2fa: passkey` + `twofa_within_seconds: N`
turns an admin action into a 2FA-gated call. The CA:

1. On the inbound admin call, calls `passkey_check_2fa(admin)`.
2. If the admin's 2FA cache entry is fresh (`< N` seconds old),
   the call proceeds.
3. Otherwise, the CA starts a ceremony via the broker
   (`POST /broker/ceremony`), returns 202 Accepted to mssh-admin
   with the ceremony id + approval URL + poll URL.
4. mssh-admin polls; on approval, the CA updates the per-admin
   2FA cache and the CLI retries the original action.
5. AAGUID allowlist is enforced at ceremony complete (the
   credential's AAGUID must be in `ca-config.yaml`
   `admin_2fa.aaguid_allowlist`).

v1 gated handlers (per `ca-config.yaml` `admin_2fa.protected_actions`):
`admin.add`, `admin.remove`, `user.remove`, `cert.revoke`.
Operators widen the list to gate more actions.

#### §4.3.9  Passkey RP — external-tool flow ✅

`/v1/external/passkey/*` is the surface external tools use as
their own RP. The cross-cutting story is §13.6.

Endpoints:
- `POST /v1/external/passkey/challenge` — start a ceremony.
- `GET  /v1/external/passkey/ceremony/<id>` — poll.
- `DELETE /v1/external/passkey/ceremony/<id>` — cancel.
- `POST /v1/external/passkey/enroll-begin` — bind a credential.

Cross-tool isolation: every endpoint matches the calling
tool-cert's tool-id against the ceremony's owning tool-id. Cross
tool calls return 404.

`outcome_url_prefix` enforcement: when the tool registers, it
declares a URL prefix; the CA's callback worker only delivers
outcomes to URLs whose host + path prefix matches. A compromised
tool cert cannot redirect outcomes elsewhere.

#### §4.3.10  Cert renew endpoint ✅

`POST /v1/cert/renew` — **not** under `/v1/admin/`. The caller
authenticates with their existing mTLS cert; the cert IS the
credential.

Rules:
- Caller's cert must chain to one of the user-facing intermediates
  (`auth` for users/admins, `host-mint` for servers).
- Caller's cert must be in the **renew window**: `not_after − now
  < 30 days` (configurable).
- Past-grace cutoff: if `now − not_after > 7 days`, refuse —
  forces a re-enrollment via the admin flow.
- Out-of-window: return 200 with `status: "too_early"` (the
  systemd timer reads this and skips).

Renewal preserves: CN, all SANs, all EKU bits, all custom mssh
markers, the original validity duration (capped by policy).
Operator can pass `revoke_predecessor: true` to revoke the old
serial in the same call.

This endpoint, plus mssh-admin's `cert renew` helper (§7.3.3)
and the systemd `cert-renew@.timer` template (§15.9), implement
§13.4 cert auto-renewal.

#### §4.3.11  Auxiliary issuance 🟡

mssh-ca as a step-ca parallel. Mint X.509 / OpenVPN / WireGuard
leaves for non-mssh applications. v1 inventory:

- ✅ `mssh-admin cert mint --type tls-server --cn X.example.com`
  — X.509 generic TLS server cert.
- ✅ `mssh-admin cert mint --type tls-client` — X.509 generic TLS
  client cert.
- ✅ `mssh-admin openvpn issue --cn alice` — OpenVPN client cert.
- ✅ `mssh-admin wireguard ...` — WireGuard keypair + config
  template.
- 🟡 PGP — open. Designed; not implemented.

Every auxiliary leaf carries a CRLDP pointer to the CA's CRL for
its issuing intermediate, so external relying parties can check
revocation without a custom protocol.

Per §2.3, auxiliary leaves are signed by intermediates other
than `user-mint` (typically `host-mint` for TLS server,
operator-chosen for OpenVPN/WireGuard), so they cannot be
presented as authz certs.

Cross-cutting story in §13.7; 3rd-party integration angle in
§15.2.

#### §4.3.12  Per-connection inner-sshd config render ✅

For msshd hosts running `inner.mode: per-connection` (§5.3.11),
the CA renders a per-session sshd_config and returns it in the
authorize response.

Template system:
- Per-server / per-group / fleet-default / built-in (precedence
  in that order).
- Marker grammar: `{LOCAL_*}` (msshd substitutes), `{FROMCA_*}`
  (CA substitutes from policy).
- Marker names: `[A-Z][A-Z0-9_]*` with optional default
  `{NAME:default}`.

Known markers (v1, full table in §14.3.2):

| Marker | Substituted by | Source |
|--------|----------------|--------|
| `{LOCAL_PORT}` | msshd | inner sshd's bound port |
| `{LOCAL_HOST_KEY}` | msshd | inner host key path |
| `{LOCAL_USER_CA_PUBKEY}` | msshd | msshd's local user-CA pubkey path |
| `{LOCAL_BANNER_FILE}` | msshd | pre-auth banner file path |
| `{FROMCA_FORCE_COMMAND}` | CA | policy `force_command` |
| `{FROMCA_ALLOW_TCP_FORWARDING}` | CA | policy `allow_tcp_forwarding` |
| `{FROMCA_SET_ENV}` | CA | policy `environment` |
| `{FROMCA_BANNER}` | CA | policy `banner` |

The rendered config is **CA-signed** — the same authorize-response
signing covers it, so msshd knows the config came from the CA and
wasn't tampered with on the wire.

#### §4.3.13  Server entrypoint + config ✅

Console-script `mssh-ca` (entrypoint:
`packages/mssh-ca/src/mssh/ca/server.py:main`). Loads

## §5  Module: msshd

The server-side gateway daemon. Mandatory in every v1 deployment.

### §5.1  Purpose ✅

msshd is the **outer-facing** SSH gateway. Per-mode behavior:

- **fallback (§1.4.1):** terminate TCP, proxy to the operator's
  existing sshd. No CA, no mTLS.
- **gated (§1.4.2, 🚧):** terminate outer mTLS, call the CA, on
  approval proxy to the operator's existing sshd.
- **enforce (§1.4.3):** terminate outer mTLS, call the CA, mint
  an ephemeral OpenSSH user cert, hand off to a hermetic inner
  sshd that msshd controls.

msshd is the only mssh component that runs unprivileged but
binds a low port (typically 22). Single OS user (`_msshd`),
filesystem state under `/var/lib/mssh/`, logs to
`/var/log/mssh/`.

### §5.2  Interconnections ✅

| Direction | Other party | Wire | Endpoints |
|-----------|------------|------|-----------|
| Inbound | mssh client | TLS 1.3 + mTLS (§3.1) | outer TCP listener port |
| Inbound | mssh-admin (local diagnostics) | unix socket | msshd-admin CLI |
| Outbound | mssh-ca | mTLS HTTPS (§3.2) | `/v1/authorize`, `/v1/crl`, `/v1/cert/renew` |
| Outbound | inner sshd | localhost SSH (§3.4) | 127.0.0.1:<rand> |
| Outbound (fallback/gated) | operator's existing sshd | raw TCP | `passthrough.upstream_host:port` |
| Filesystem | state dir | local | `<state_dir>/authz_cache.json`, CRL state, host keys, local user-CA key |

### §5.3  Implementation

#### §5.3.1  Listener entrypoint + mode selector ✅

Console-script `msshd` (entry: `packages/msshd/src/mssh/msshd/__main__.py`).

Boot sequence:
1. Read `msshd.yaml` from `--config` (default
   `/etc/mssh/msshd.yaml`).
2. Validate every security-relevant field is present (§13.9.7).
   Refuse to start otherwise.
3. Load the appropriate trust roots (`auth_trust_root` for client
   mTLS, `bypass_trust_root` for bypass certs, `host-mint` for
   mssh-ca's server cert — chain-pinning per §2.3).
4. Open the listening socket.
5. Route accepted connections to `enforce_listener.py`,
   `gated_listener.py`, or `fallback_listener.py` per
   `mssh.yaml: mode:`.

The mode selector is a one-line dispatch — once routed, the
appropriate handler owns the connection. Mode flips require
restart.

#### §5.3.2  Fallback handler ✅

Pure TCP proxy. Single asyncio task per connection: read from the
outer socket, write to `passthrough.upstream_host:port`. No
parsing, no CA call, no certificate handling.

Used during initial adoption to wire mssh into the network path
without changing authentication semantics. Operator's existing
sshd still terminates SSH on port 22 (typically moved to a
different port and msshd-fallback takes 22).

Configuration:
```yaml
mode: fallback
fallback:
  upstream_host: 127.0.0.1
  upstream_port: 22022
```

#### §5.3.3  Gated handler 🚧 P2 (v1 ship blocker)

Outer mTLS + CA approval → proxy to operator's existing sshd at
their canonical port. No ephemeral cert mint; no hermetic inner
sshd.

Flow (planned):
```
1. accept outer TCP.
2. terminate TLS 1.3 + mTLS; validate client cert chains to auth.
3. read JSON header (§3.1) carrying user + command intent.
4. authz-cache lookup (§5.3.5); on miss, POST /v1/authorize.
5. on grant: open TCP to gated.upstream_host:port (operator's sshd).
6. proxy outer↔inner raw bytes (the operator's sshd does its own
   auth from inside the TLS tunnel — the operator's existing SSH
   key material works unchanged).
7. on deny: close outer with DENY frame (§3.1).
```

Configuration (planned):
```yaml
mode: gated
gated:
  upstream_host: 127.0.0.1
  upstream_port: 22022
ca: { ... }                # same as enforce
outer_mtls: { ... }        # same as enforce
```

Estimated scope: ~300-500 LOC + ~20 tests. Required to ship v1
per §1.4.2 + FEATURES-TODO row.

#### §5.3.4  Enforce handler ✅

The production path. Code: `enforce_listener.py`.

Flow:
```
1. accept outer TCP.
2. terminate TLS 1.3 + mTLS; client cert must chain to
   ca.auth_trust_root (§2.3).
3. read JSON header (§3.1); extract user + command + framing flag.
4. {bypass-cert injection path: §5.3.7}
5. authz-cache lookup keyed by (mTLS subject, claimed user).
6. miss → POST /v1/authorize to mssh-ca (carry last_crl_seqs).
7. response → store in cache tagged 'ca'; apply CRL drift sync
   (§5.3.8); enforce strict-mode gate if needed (§5.3.9).
8. mint ephemeral OpenSSH user cert via local user-CA (§5.3.13)
   carrying principal + critical-options from authz cert.
9. open SSH session to hermetic inner sshd on localhost, present
   ephemeral cert.
10. inner sshd auths the cert; opens session/exec channel.
11. proxy frames between outer (mssh client) and inner (sshd
    channel) until close.
12. on close: send EXIT frame; close.
```

Implements §1.4.3.

#### §5.3.5  Authz cache ✅

Code: `authz_cache.py`. Cross-cutting story: §13.1.

In-memory dict keyed by principal (the `(user, host)` extracted
from the mTLS subject + the session-RPC user field). Each entry:

```python
@dataclass
class AuthzEntry:
    cert: x509.Certificate
    serial: str
    not_before: datetime
    not_after: datetime
    source: Literal["ca", "bypass"]
    injected_at: datetime
    last_used_at: datetime
```

Operations:
- `get(principal) -> AuthzEntry | None` — used by §5.3.4 step 5.
- `put(principal, cert, source="ca")` — store.
- `invalidate_by_principal(principal)` — on CA deny.
- `invalidate_by_serial(serial)` — on CRL apply (§5.3.8).

Persistence: on every put/invalidate, msshd serializes the cache
to `<state_dir>/authz_cache.json` (mode 0600) via atomic write
(temp file + rename). Survives restart.

Per-issuer CRL state:
```python
class AuthzCache:
    last_crl_seqs: dict[str, int]  # {issuer_id: seq}
```

This map is maintained alongside the cache; it's the `last_applied_seqs`
that §5.3.8 advances and that §5.3.9 inspects.

#### §5.3.6  Authz cache eviction ✅

`performance.authz_cache_max_per_principal` (default 10) and
`performance.authz_cache_max_total` (default 10000).

- **max_per_principal** — primary fairness primitive. Today the
  cache is principal-keyed, so this has no observable effect
  (replaces-on-put). Forward-compat: if the cache key broadens
  to `(principal, identity_fingerprint)`, this caps the per-user
  fanout.
- **max_total** — operative control. FIFO eviction of the
  globally-oldest entry (by `injected_at`) when total exceeds
  cap. Logged WARNING per eviction.

**Source-agnostic** — bypass entries follow the same rules. A
recently-injected bypass is MRU and won't be near eviction;
a long-dormant one is fair game.

Liveness implication (not a regression): evicting a valid entry
forces the next connection from that principal to re-call the CA.
CA-down at that moment → brief deny for that principal. Equivalent
to a cold-restart cache.

Listed as §13.9.3 hardening member (already ✅, regression
guard).

#### §5.3.7  Bypass-cert injection ✅

Code: `enforce_listener.py::_handle_bypass_injection`. Cross-cutting
story: §13.2.

When the mssh client sends `--inject-bypass-cert`, the JSON
header carries `bypass_cert: "<base64 PEM>"`. msshd validates:

1. **Chain pinned to `bypass_trust_root`** (separate from
   `auth_trust_root`, per §2.3). The chain must walk leaf →
   `bypass-mint` intermediate (must equal pinned cert) → Root.
   A leaf signed by `user-mint` or `auth` is refused.
2. **Critical marker `OID_CA_BYPASS` present.** A normal
   `user-mint`-signed authz cert (which lacks this marker) cannot
   be injected — even if presented with the bypass flag, it fails
   step 1 because it doesn't chain to `bypass-mint`.
3. **Within validity window** (`not_before ≤ now ≤ not_after`).
4. **mTLS-principal-match.** The bypass cert's principal must
   equal the principal claimed by the mTLS handshake. Prevents a
   stolen bypass cert being injected by an attacker who has a
   different mTLS cert.
5. **Not already revoked.** Check `<state_dir>/crl/<issuer_id>.jsonl`
   for the serial; refuse if present.

On success: `authz_cache.put(principal, cert, source="bypass")`,
ack via JSON, close. No session is opened on the bypass-injection
call.

Operator UX is the two-step:
```sh
mssh --inject-bypass-cert alice-bypass.crt srv-acct
mssh srv-acct -- whoami        # next call: cache hit
```

Listed as §13.9.5 hardening member.

#### §5.3.8  CRL sync ✅

Code: `crl_sync.py`. Cross-cutting story: §13.3.

Triggered by per-issuer `current_crl_seqs` returned in every
`/v1/authorize` response. msshd's `AuthzCache.last_crl_seqs[issuer_id]`
is the `last_applied_seqs` per issuer.

Algorithm:
```
for issuer_id, current_seq in response.current_crl_seqs.items():
    last = cache.last_crl_seqs.get(issuer_id, 0)
    if current_seq > last:
        # schedule background fetch (off the authorize hot path)
        task_queue.put((issuer_id, last + 1, current_seq))

# worker
for (issuer_id, after, target) in queue:
    while after <= target:
        entries = ca_client.get_crl(issuer_id, after=after - 1,
                                     limit=ca.crl_fetch_limit)
        for entry in entries:
            for serial in entry.serials:
                authz_cache.invalidate_by_serial(serial)
            after = entry.seq + 1
        cache.last_crl_seqs[issuer_id] = entry.seq
        cache.persist()
```

Per-issuer because §2.5 keeps issuers independent — a revocation
against `bypass-mint` doesn't pollute `user-mint`'s CRL state.

#### §5.3.9  Strict-mode gate ✅

When the sum of per-issuer gaps exceeds `ca.crl_strict_threshold`
(default 50; 0 disables), msshd refuses cache hits and forces a
live CA call for every authorize, until the gap is fully closed.

Rationale: bounds the staleness window after a long network
partition. With a 50-entry threshold and typical revocation rates,
the gate triggers only after meaningful drift; routine operation
never hits it.

Listed as §13.9.4 hardening member.

#### §5.3.10  Hermetic inner sshd — long-lived ✅

Default `inner.mode: long_lived`. One sshd subprocess spawned at
msshd boot, serves every session afterward.

Config rendered once from a built-in template
(`packages/msshd/.../templates/inner_sshd.long_lived.conf.tmpl`):

```sshd_config
Port {LOCAL_PORT}
ListenAddress 127.0.0.1
HostKey {LOCAL_HOST_KEY}

PermitRootLogin no
PasswordAuthentication no
ChallengeResponseAuthentication no
PubkeyAuthentication yes
AuthorizedKeysFile none
TrustedUserCAKeys {LOCAL_USER_CA_PUBKEY}
RevokedKeys none

UsePAM no
UseDNS no
AcceptEnv none

LogLevel INFO
SyslogFacility AUTH
ChrootDirectory none
StrictModes yes

# Hermetic invariants — DO NOT MODIFY
Subsystem none
Include /dev/null
Match all
    PermitOpen none
    AllowAgentForwarding no
    AllowTcpForwarding no
    PermitTunnel no
    X11Forwarding no
```

`{LOCAL_*}` markers substituted by msshd at startup.

Invariants enforced (verified by `sshd -t` + a config-hash
check):
- Listens only on `127.0.0.1`.
- Trusts only msshd's local user-CA.
- No PAM, no Include, no Match overrides.
- AEAD ciphers only; ed25519 + ecdsa-p256 host keys only.
- Logs to msshd's stderr.

No per-session policy variability in the config itself; per-session
policy lives on the ephemeral OpenSSH cert (critical-options).

#### §5.3.11  Hermetic inner sshd — per-connection ✅

Optional `inner.mode: per_connection`. Fresh sshd subprocess per
session. The CA renders the sshd_config (§4.3.12) and msshd:

1. Receives the CA-signed `inner_sshd_config` in the authorize
   response.
2. Substitutes its own `{LOCAL_*}` markers (port, host key,
   user-CA pubkey, banner file).
3. Validates with `sshd -t -f <rendered>` (refuses to spawn on
   syntax error).
4. Writes to a temp file with mode 0600.
5. Spawns `sshd -D -e -f <rendered>` as a subprocess.
6. Connects with the freshly-minted ephemeral cert.
7. On session close, terminates the sshd subprocess and
   deletes the temp file.

Per-session overhead ~50-100ms. Unlocks per-user banner
substitution and OpenSSH-native enforcement of per-session policy
(`ForceCommand`, `SetEnv`, `AllowTcpForwarding`) without an
application-layer policy translator on msshd.

The rendered config is **CA-signed** — the authorize response's
signature covers the config text, so msshd can verify the CA
didn't get tampered with on the wire.

#### §5.3.12  Emergency template (per-connection break-glass) ✅

Per-connection mode depends on the CA to render. To keep break-glass
recovery from depending on the CA being up, msshd ships a local
**emergency template** at `/usr/share/mssh/sshd_config.emergency.template`
(operator override at `/etc/mssh/sshd_config.emergency.template`)
that uses only `{LOCAL_*}` markers.

When CA is unreachable **and** an emergency cert is configured in
`msshd.yaml`, msshd renders the emergency template locally and
spawns the per-session sshd from it. Same safe-by-default posture
as a normal hermetic config, but with no per-session policy
(no `{FROMCA_*}` markers).

Rate-limited: minutes between uses, not seconds, so an emergency
mode is obvious in the audit log.

Operators whose break-glass story is simpler (system sshd on a
different port) should leave the emergency cert unconfigured and
flip to `mode: fallback` instead.

#### §5.3.13  Local user-CA ✅

Per-msshd keypair, generated at first boot and stored at
`<state_dir>/user_ca.{pem,pub}` (mode 0600 for the key). **Never
leaves the msshd host.**

Sole purpose: sign ephemeral OpenSSH user certs that the
hermetic inner sshd will accept. The pubkey is the value of
`TrustedUserCAKeys` in the inner sshd's config.

Cert profile (OpenSSH cert format):
- principal: extracted from the authz cert's `OID_AUTHZ_PRINCIPAL`.
- valid_from / valid_to: bracket the session window (default
  `now ± 5min`).
- critical_options: `force-command`, `source-address`,
  `permit-X11-forwarding`, `permit-pty`, etc., copied from the
  authz cert's policy_summary.
- key_id: msshd's request_id (correlation with audit log).

Rotation procedure: `msshd-admin user-ca rotate` generates a new
pair, writes it alongside the old, and signals msshd (SIGHUP) to
re-read. Inner sshd re-loads `TrustedUserCAKeys`. Existing
ephemeral certs minted by the old key remain valid until natural
expiry.

#### §5.3.14  msshd-admin diagnostic CLI ✅

Local-only CLI for the msshd host's operator. Communicates with
msshd over a unix socket at `/run/mssh/msshd-admin.sock`
(group-readable by `_msshd`).

Commands (full surface §14.2.3):
- `msshd-admin status` — running mode, listener port, CA URL,
  cache size, CRL gap per issuer.
- `msshd-admin authz-cache show [principal]` — inspect cache
  entries.
- `msshd-admin authz-cache invalidate <principal>` — manual
  eviction.
- `msshd-admin user-ca rotate` — rotate local user-CA (§5.3.13).
- `msshd-admin reload` — SIGHUP equivalent.

No mTLS; access control is OS user (you must run as `root` or
`_msshd`).

#### §5.3.15  Pre-auth banner ✅

The hermetic inner sshd serves a banner before SSH authentication
completes (after key-exchange, before the cert is validated).
Useful for legal-disclosure text or operator branding.

Configuration:
```yaml
inner:
  banner:
    text: |
      *** Property of Example Corp. ***
      Unauthorized access prohibited.
```

The banner is written to a file at msshd boot and referenced via
`{LOCAL_BANNER_FILE}` in the inner sshd template. In per-connection
mode, the CA can override per-user via `{FROMCA_BANNER}` (§4.3.12).

## §6  Module: mssh (client) ✅

The user-facing client. Mandatory in every v1 deployment. Single
Python module `packages/mssh/src/mssh/client.py`.

### §6.1  Purpose ✅

`mssh` is the operator-facing command-line. It opens a TLS+mTLS
connection to msshd, emits a typed-framed session-RPC header, and
acts like a thin SSH client wrapper from then on. Behavior matches
`ssh` for the user — same arg-parsing, same exit codes, same
TTY/agent semantics — so existing scripts and SSH-aware tooling
work unchanged.

### §6.2  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Inbound | user shell | stdin/stdout/stderr/argv | TTY pass-through |
| Outbound | msshd | TLS 1.3 + mTLS (§3.1) | one connection per session |
| Filesystem | `~/.mssh/` | local | client cert + key + trust root + endpoint config |

### §6.3  Implementation

#### §6.3.1  Config resolution ✅

Search order on every invocation:

1. CLI flags (`--cert`, `--key`, `--trust`, `--endpoint`).
2. Environment variables (`MSSH_CERT`, `MSSH_KEY`, `MSSH_TRUST`,
   `MSSH_ENDPOINTS`).
3. `~/.mssh/config.yaml`.
4. Built-in defaults.

`~/.mssh/` layout (§14.3.3):
```
~/.mssh/
  cert.pem        # auth-signed mTLS client cert
  key.pem         # mode 0600
  trust.pem       # host-mint intermediate (msshd cert validation)
  config.yaml     # endpoint list + per-host overrides
```

`config.yaml`:
```yaml
endpoints:
  - host: msshd-prod-01.example.com
    port: 22
  - host: msshd-prod-02.example.com   # failover (§6.3.3)
    port: 22

host_overrides:
  srv-acct-01:
    user: alice                       # claimed principal in session-RPC
```

#### §6.3.2  TLS handshake + session-RPC ✅

Two-stage open:

1. TCP connect → TLS 1.3 ClientHello carrying the client cert.
   Cipher suites per §3.1; SNI = msshd hostname. Validate
   msshd's server cert chains to `trust.pem` (host-mint pin per
   §2.3).
2. Write JSON header line:
   ```json
   {"v": 1, "user": "alice", "command": ["whoami"],
    "interactive": false, "supports_framing": true}
   ```
3. Read JSON ack. On `ok: false`, print denial reason; exit 6.
4. On `ok: true, framing: true`, switch to typed framing
   (§3.1 + §14.7). Otherwise, raw byte pump (v1.0 compat).
5. Pump: select() over stdin + socket. Send STDIN/STDIN_EOF/WINSIZE;
   receive STDOUT/STDERR/BANNER/EXIT/SIGNAL/DENY/CLOSE.
6. On EXIT frame, exit with that code. On SIGNAL frame, exit
   `128 + signum`. On DENY frame, exit 6.

#### §6.3.3  Endpoint failover ✅

The endpoint list is tried in order. Each endpoint is given one
TLS handshake attempt. On TLS failure (timeout, unreachable, cert
mismatch), try the next. Once one succeeds, no further fallback —
if that one denies, the call denies.

**No automatic retry against a different identity.** Clock skew,
revoked cert, or wrong-claim-user errors must be addressed by the
operator, not papered over by trying a different endpoint.

#### §6.3.4  Bypass-cert injection (`--inject-bypass-cert`) ✅

Two-step operator UX (§13.2):
```sh
mssh --inject-bypass-cert alice-bypass.crt srv-acct
mssh srv-acct -- whoami        # next call: cache hit
```

The first call:
- Opens the TLS handshake as normal.
- Sends a JSON header that includes `bypass_cert: "<base64 PEM>"`
  in addition to the usual fields.
- Reads ack. On success: print "injected"; exit 0. On failure:
  print rejection reason; exit non-zero.
- Closes (no session frames are exchanged).

#### §6.3.5  Local-port forwarding (`-L`) 🚧 P3 (v1 target)

SSH-equivalent `-L local_port:remote_host:remote_port` for
tunneling. Required to unblock §11.3.5 (admin-web via
mssh-tunneled localhost). ~150 LOC.

Once landed: `mssh -L 9443:localhost:9443 mssh-ca-host` opens a
tunnel where a browser at `https://localhost:9443/` reaches the
mssh-admin-web instance on the CA host's localhost.

## §7  Module: mssh-admin ✅

The operator CLI. Mandatory in every v1 deployment.

### §7.1  Purpose ✅

`mssh-admin` is the only first-party CLI for the mssh-ca admin
API. It wraps `/v1/admin/*` calls in click-style subcommands,
handles the 2FA polling pattern, formats output for humans + JSON
consumers, and embeds the cert-renew helper (§13.4).

Optional: `mssh-admin-web` (§11) for the same operations via
browser; `mssh-mcp` (§12) for the same operations via an AI agent.
Both are explicitly NOT part of `mssh-admin` because they have
different threat models and are independently optional.

### §7.2  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Outbound | mssh-ca | mTLS HTTPS (§3.3) | `/v1/admin/*` |
| Outbound | mssh-passkey browser-side | browser-launch | the operator's browser opens the approval URL |
| Filesystem | `~/.mssh-admin/` | local | admin mTLS cert + key + cache |

### §7.3  Implementation

#### §7.3.1  CLI command tree ✅

Top-level subcommands (full surface §14.2.2):

```
mssh-admin server   {add, remove, groups, list}
mssh-admin user     {add, remove, key, list}
mssh-admin admin    {add, remove, list}
mssh-admin policy   {add, remove}
mssh-admin cert     {mint, revoke, renew}
mssh-admin intermediate {list, rotate, mint-external}
mssh-admin external-tool {add, remove, list}
mssh-admin bypass-cert {mint, list, revoke}
mssh-admin audit    {tail, search}
mssh-admin template {set, unset, list, show}
mssh-admin openvpn  {issue, revoke}
mssh-admin wireguard {peer-add, peer-list, peer-remove}
mssh-admin pki      {mint-user, ...}     # 🟡 promotion from scripts/
mssh-admin status                       # quick health check
```

Each subcommand:
1. Loads the admin's mTLS cert from `~/.mssh-admin/cert.pem`.
2. Makes the appropriate `/v1/admin/*` call.
3. Handles 202-Accepted via §7.3.2.
4. Formats response per `--output` (§7.3.5).
5. Exits non-zero on any deny / error.

#### §7.3.2  2FA polling loop ✅

Code: `mssh.admin.main::_handle_2fa_call`. Cross-cutting story:
§13.5.

When mssh-ca returns 202 Accepted with a ceremony body, the CLI:
```
1. Print the approval URL to stderr. In a TTY (v0.3.2+), render
   it as a terminal QR code so the operator can scan with their
   phone without copy-paste.
2. Poll GET /v1/admin/passkey/ceremony/<id> every 2s, with a
   total timeout of `ttl_s` (from the response).
3. On status=="approved": retry the original call once. The
   retry succeeds because the CA has cached the per-admin 2FA
   window.
4. On status=="denied" / "expired" / TTL elapsed: exit non-zero.
```

v1 4 gated handlers: `admin.add`, `admin.remove`, `user.remove`,
`cert.revoke`. Operators widen via `ca-config.yaml`.

#### §7.3.3  Cert auto-renewal helper ✅

`mssh-admin cert renew --cert ... --key ... --out-cert ...
--out-key ... [--threshold-days N] [--revoke-old] [--on-renew CMD]`

Behavior:
- Reads the local cert, computes `days_until_expiry`.
- If `> threshold_days` (default 7), exits 0 silently. Safe to
  run daily.
- Otherwise calls `POST /v1/cert/renew` (§4.3.10) with the local
  cert as the credential.
- On 200 + `status: "ok"`, writes new cert/key atomically (temp
  + rename, mode 0600 for the key).
- If `--revoke-old` is set, the renew call carries
  `revoke_predecessor: true`.
- If `--on-renew CMD` is set, runs CMD (e.g. systemd reload).

systemd integration: ships `systemd/cert-renew@.service` +
`cert-renew@.timer` templates (§15.9). `OnCalendar=daily`,
`RandomizedDelaySec=30m` so 1000 services don't all hit
mssh-ca at 00:00.

#### §7.3.4  PKI ceremony helpers ✅

```
mssh-admin intermediate list
mssh-admin intermediate rotate <role> [--force]
mssh-admin intermediate mint-external --name <X> --path-length N
```

Implementations per §2.5 + §2.6. `list` shows every intermediate
with `issuer_id` (`<role>:<fp16>`) + validity window + count of
unexpired leaves issued under it.

🟡 `mssh-admin pki` subcommand is a v1-target piece: promote
`scripts/mint-user-pki.py` to a first-class subcommand
(~120 LOC).

#### §7.3.5  Output formatters ✅

`--output` selects:
- `human` (default) — tabular, colorized when TTY.
- `json` — single JSON object on stdout, status on stderr.
- `quiet` — only the primary identifier (one per line).

Used by scripted automation:
```sh
for s in $(mssh-admin server list --output quiet); do
  mssh-admin cert renew --target $s ...
done
```

#### §7.3.6  Local state ✅

`~/.mssh-admin/`:
```
cert.pem         # auth-signed admin mTLS cert
key.pem          # mode 0600
trust.pem        # host-mint intermediate for CA validation
ca-url           # CA endpoint URL
cache/           # response cache for read-only calls (5s TTL)
```

No long-lived tokens. The mTLS cert IS the credential — same
posture as §4.3.10 cert-renew (no admin role bearer token).

## §8  Module: mssh-passkey ✅

The WebAuthn broker. **Optional** — required only when admin-2FA
(§13.5) or external-tool RP (§13.6) is in use. Separately
deployable (its own systemd unit, its own apache2 vhost).

### §8.1  Purpose ✅

mssh-passkey is a public-facing relay between an RP (mssh-ca, or
an external tool registered via §3.5) and the user's browser.
Holds no key material; stores only short-lived ceremony state.

Why a broker exists at all (instead of mssh-ca serving the
WebAuthn pages directly): mssh-ca lives on a private network and
should never accept browser traffic from the internet. The broker
is the internet-facing piece; mssh-ca interacts with it over
mTLS from inside the trusted network.

### §8.2  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Inbound | browser (user agent) | HTTPS (apache2-terminated) | `/register/<id>`, `/approve/<id>` |
| Inbound | mssh-ca (RP) | mTLS HTTPS (§3.6) | `/broker/ceremony[/<id>]` |
| Inbound | external tool (RP) | mTLS HTTPS (§3.6) | `/broker/ceremony[/<id>]` |
| Outbound | RP (mssh-ca or external tool) | mTLS HTTPS | callback delivery to RP's `outcome_url` |
| Filesystem | broker dir | local | `ceremonies.sqlite` + mTLS cert |

### §8.3  Implementation

#### §8.3.1  Storage ✅

Single SQLite database, single table `ceremonies` (§14.6 schema):

```sql
CREATE TABLE ceremonies (
    id TEXT PRIMARY KEY,
    rp_id TEXT NOT NULL,
    rp_outcome_url TEXT NOT NULL,
    kind TEXT NOT NULL,            -- 'register' | 'approve'
    user_handle TEXT,
    challenge_b64 TEXT NOT NULL,
    status TEXT NOT NULL,          -- 'pending' | 'approved' | 'denied' | 'expired'
    credential_b64 TEXT,           -- populated on approve
    aaguid TEXT,                   -- populated on approve
    ttl_seconds INTEGER NOT NULL,
    created_at TEXT NOT NULL,
    completed_at TEXT,
    callback_attempts INTEGER DEFAULT 0,
    callback_last_at TEXT,
    callback_status TEXT           -- 'pending' | 'delivered' | 'failed'
);
```

Single table by design — the broker holds no per-user state and
no key material. Every ceremony is short-lived; expired ceremonies
are deleted by §8.3.5.

#### §8.3.2  Broker API ✅

mTLS-gated endpoints (CN forwarded by apache2 as `X-Client-CN`):

```
POST   /broker/ceremony       — start a ceremony, returns id + approval_url
GET    /broker/ceremony/<id>  — poll status
DELETE /broker/ceremony/<id>  — cancel
```

The broker matches `X-Client-CN` against a registered RP
allowlist (mssh-ca's CN + each external tool's CN). Cross-RP
calls return 404 (a tool can't read mssh-ca's ceremonies, and
vice versa).

#### §8.3.3  Public browser pages ✅

```
GET /register/<id>   — Bootstrap5 page; vanilla JS calls navigator.credentials.create()
GET /approve/<id>    — Bootstrap5 page; vanilla JS calls navigator.credentials.get()
```

The JS driver:
1. Fetches challenge from `/broker/ceremony/<id>/challenge`.
2. Calls WebAuthn API.
3. POSTs the result to `/broker/ceremony/<id>/complete`.
4. Shows success/failure message.

The browser sees the broker's domain as the RP — important for
WebAuthn credential binding. The credential the user creates is
bound to the broker's hostname, **not** to mssh-ca's. This is
the whole point of the relay model: the RP-from-the-browser's
perspective is stable across mssh-ca rotations.

#### §8.3.4  Callback delivery worker ✅

On ceremony completion (approved / denied / expired), the broker
queues an outbound POST to the RP's `outcome_url`:

```json
{"ceremony_id": "...", "status": "approved",
 "credential_b64": "...", "aaguid": "..."}
```

Retry schedule (exponential):
- Attempt 1: immediate.
- Attempt 2: +5s.
- Attempt 3: +30s.
- Attempt 4: +2m.
- Attempt 5: +10m.
- Then: abandon, mark `callback_status: failed`.

Outbound uses the broker's own mTLS cert to authenticate to the
RP — same `host-mint`-issued cert it uses to receive RP calls.

#### §8.3.5  TTL expiry sweeper ✅

Background thread, 30s tick:
1. Find ceremonies with `status='pending' AND
   created_at + ttl_seconds < now`.
2. Mark `status='expired'`, schedule §8.3.4 callback.
3. Delete ceremonies with `status IN ('approved','denied','expired')
   AND completed_at + retention_window < now` (default 24h
   retention).

#### §8.3.6  Front-end variants ✅

```yaml
front_end: apache    # production: apache2 reverse proxy terminates TLS
# OR
front_end: dev       # lab: broker terminates TLS in-process (single port)
```

Production: apache2 listens on 443 with a public TLS cert; reverse
proxies `/broker/*` to the broker's mTLS port (forwarding
`X-Client-CN`) and `/register/*` + `/approve/*` to the broker's
HTTPS port without mTLS.

Lab: broker binds two ports directly. No apache2 needed.

#### §8.3.7  Hardening v2 (anti-compromised-broker) 🚧 P2 — v1 ship blocker (unconditional)

The broker is internet-facing and a high-value target. v1
hardening assumes it can be compromised and defends the RP
(mssh-ca + external tools) accordingly. The defenses **live on
the CA receiver side**, not on the broker — so they ship even
when the broker isn't deployed.

Members:

- **Injection defense.** The RP's callback receiver validates
  the `ceremony_id` against an RP-local pending-ceremonies list
  (the RP-side counterpart that mssh-ca maintains anyway for
  the polling loop). An attacker who runs a malicious broker
  can't forge outcomes for ceremonies the RP didn't start.
- **Replay defense.** Each ceremony id is consumed once; a
  re-delivered callback (same id, second time) is dropped.
- **DoS rate limit.** Per-source-IP and per-RP-tool rate limits
  on callback POSTs.
- **Bogus-callback rejection.** Outcomes from URLs that don't
  match the registered RP's outcome receiver (the CA's broker
  callback endpoint, mTLS-authenticated by the broker's own
  cert) are dropped.
- **2FA fail-state mode.** A new `admin_2fa.fail_state:
  fail-closed | fail-open` setting in `ca-config.yaml`. Default
  `fail-closed` — if the broker is unreachable or returning
  garbage, gated admin actions deny rather than silently allow.

Listed as §13.9.1 hardening member, **v1 ship blocker
unconditionally** even when the broker is not enabled.

## §9  Module: mssh-common ✅

The shared library. No runtime presence. Imported by mssh, msshd,
mssh-admin, debug_sshd. Mandatory.

### §9.1  Purpose ✅

Single implementation of every cross-component primitive: HTTP-to-CA
client, mTLS cert handling, the typed-framing protocol, the
config-loader surface, the SQLite-backed local cache. If two
components both need behavior X, X lives here.

Also houses `akc_shim`, the OpenSSH AuthorizedKeysCommand entry
point (an executable that links mssh-ca to an unmodified OpenSSH).

### §9.2  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Imported by | mssh, msshd, mssh-admin, debug_sshd | Python import | every CA-calling component |
| `akc_shim` outbound | mssh-ca | mTLS HTTPS (§3.2 subset) | per-AKC-invocation /v1/authorize |

### §9.3  Implementation

#### §9.3.1  shim — CA client ✅

Code: `packages/mssh-common/src/mssh/shim/ca_client.py`.

`CaClient` class wraps `requests` with:
- mTLS context (cert + key + trust root).
- Retry/backoff with jitter (3 attempts, exponential).
- Structured error types: `CaUnreachable`, `CaDenied`,
  `CaInvalidResponse`, `CaProtocolMismatch`.
- Per-call timeout (default 5s for `/v1/authorize`, 30s for CRL).

Callers receive typed Python objects, not raw JSON. All
JSON-shape evolution stays here; consumers don't see schema
drift.

#### §9.3.2  shim — config helpers ✅

Code: `shim/config.py`. Common parsing for:
- The `ca:` block of `msshd.yaml`.
- The endpoint list in `~/.mssh/config.yaml`.
- The `~/.mssh-admin/` layout.
- Env var fallbacks (`MSSH_*` family).

Validates against the §14.3 schemas; raises a single
`MsshConfigError` on any violation (caller catches and exits
with a friendly message). §13.9.7 default-deny is enforced here:
missing security-relevant fields raise.

#### §9.3.3  shim — local cache ✅

Code: `shim/sqlite_cache.py`. SQLite-backed kv cache used by:
- `mssh-admin` for the 5s read-only response cache.
- `msshd-admin` for status/diagnostic caching.

(NOT used by msshd's authz cache — that's a different beast at
§5.3.5, with persistence semantics tailored to its role.)

#### §9.3.4  akc_shim — OpenSSH AKC entry point ✅

Code: `packages/mssh-common/src/mssh/akc_shim/`.

Console-script `mssh-akc-shim`, invoked by sshd's
`AuthorizedKeysCommand`:

```
# /etc/ssh/sshd_config
AuthorizedKeysCommand /usr/bin/mssh-akc-shim %u %k
AuthorizedKeysCommandUser _msshd
```

The shim:
1. Reads username from argv[1], pubkey from argv[2] (or stdin
   per OpenSSH version).
2. Loads the local shim mTLS cert (host-mint signed) from
   `/etc/mssh/akc-shim/`.
3. Calls `POST /v1/authorize` with the pubkey blob.
4. On grant: print an `authorized_keys` line that includes
   the user's pubkey plus any cert critical-options translated
   from the authz cert's policy_summary. sshd then performs
   the SSH auth against this line.
5. On deny / error: exit non-zero with stderr message. sshd
   refuses the connection.

§15.6 frozen-contract details:
- stdin/argv/stdout/exit-code shape (so a re-implementation in
  Go/Rust/C honors the same contract).
- envvars read: `MSSH_AKC_CONFIG` (config path override),
  `MSSH_AKC_TIMEOUT` (per-call timeout).

Used with the optional `openssh-patches/` patches when the
operator wants extra metadata visibility (the upstream patches
expose source IP + connection metadata to AKC).

## §10  Module: debug_sshd 🟡

The diagnostic AsyncSSH-based SSH server. **Optional. NOT for
production deployments.**

### §10.1  Purpose ✅

debug_sshd is a Python AsyncSSH server that calls mssh-ca inline
during pubkey auth. Its single reason to exist: structured,
verbose, per-step logging of the auth path, for diagnosis when
production msshd misbehaves.

It is intentionally **smaller** than OpenSSH — less complete
protocol surface, easier to instrument. Several SSH features
(full PTY quirks, X11 forwarding, agent forwarding, certain cipher
suites) are best-effort or missing in debug_sshd.

Triage rules:
- If something works in debug_sshd but not in production msshd,
  that's likely a debug_sshd limitation, not a bug in production.
- If something works in production but breaks in debug_sshd,
  treat it as a debug_sshd issue first.

The adhoc lab's "debug" tier (`./setup_adhoc.sh debug`) spins
this server up. The default `./setup_adhoc.sh` (no argument)
uses production msshd + hermetic OpenSSH.

### §10.2  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Inbound | mssh or stock `ssh` client | SSH-2.0 | localhost or LAN |
| Outbound | mssh-ca | mTLS HTTPS (via §9.3.1 shim) | per-connection /v1/authorize |
| Stderr | operator terminal | JSON-Lines | step-by-step trace |

### §10.3  Implementation ✅

Code: `packages/msshd/src/mssh/debug_sshd/`.

AsyncSSH server with a custom session class:
1. Accept TCP, perform SSH-2.0 transport.
2. On `auth_pubkey_received(user, key_data)`:
   - Log: received pubkey, blob hash.
   - Call `/v1/authorize` with the pubkey blob.
   - Log: CA request/response (sanitized).
   - On grant: parse authz cert, log principal + critical-options,
     return True.
   - On deny: log reason, return False.
3. On channel open: log channel type, target.
4. On every received packet: log type + size.

Logs go to stderr as JSON-Lines, one event per line:

```json
{"ts": "...", "level": "info", "step": "auth.pubkey",
 "user": "alice", "fp": "SHA256:...",
 "result": "granted", "ca_request_id": "..."}
```

A `--trace` flag adds packet-level dumps for the truly stuck.

### §10.4  In-situ swap-in 🚧

Operator affordance: temporarily replace production msshd's inner
sshd with debug_sshd to diagnose a misbehaving session, with a
sideband channel that streams the trace to a CA audit log.

Captured idea; not implemented in v1. → §18.

**Optional.** Browser portal over the mssh-ca admin API. Disabled

### §11.1  Purpose ✅

Operators who prefer a browser to a CLI. Same actions, different

#### §11.3.1  Read-only views ✅

Flask + Bootstrap5 + vanilla JS. Pages:

Three layers:
1. **apache2** terminates TLS, validates the client cert chain

2. **mssh-admin-web** trusts `X-Client-CN` only if the request

3. **mssh-ca** does the role check on every admin call —

The recommended deployment: don't expose mssh-admin-web on the
public internet. Instead, run it on localhost on the mssh-ca host
and reach it via `mssh -L 9443:localhost:9443 mssh-ca-host`
(§6.3.5).

Server side ✅; client side depends on §6.3.5 landing.

This makes the admin web available only to operators who can
already present a valid mssh client cert and pass the CA's
policy — same access bar as `mssh-admin`, no additional internet
exposure.

## §12  Module: mssh-mcp 🟡

**Optional. OFF BY DEFAULT — attack-surface concern.** Model Context
Protocol interface to mssh-ca for trusted-AI diagnostic flows.

### §12.1  Purpose ✅

Give a sandboxed AI helper a structured, audited surface for
NL-driven diagnostics ("what changed in audit yesterday?", "list
servers where the CRL gap is over 10") and — post-v1 — trusted
config edits. Per-tool capabilities; everything mTLS-authenticated;
every action audited.

### §12.2  Threat model ✅

**MCP can be tricked.** Prompt injection can convince an
LLM-driven agent to issue a destructive admin call. Therefore:

1. **Same auth surface as mssh-admin.** Every MCP action requires
   the same mTLS + role check as the equivalent mssh-admin
   command. MCP's mTLS cert is just another admin cert.
2. **Capability subset.** The capability set the MCP exposes is
   a strict subset of mssh-admin. v1: read-mostly. Mutating
   actions are not exposed via MCP in v1.
3. **Audit tagging.** Every MCP-originated call carries
   `origin: mcp` in the audit record (§4.3.7).
4. **OFF by default.** MCP is OFF unless explicitly turned on
   by `ca-config.yaml`'s `mcp.enabled: true`.
5. **Bypass-cert mint inaccessible.** MCP cannot reach the
   bypass-cert mint path under any configuration in v1, even
   with a superuser cert. The capability allow-list (§12.4.3)
   omits it; the CA refuses bypass-cert calls with
   `origin: mcp` regardless of role.

Listed as §13.9.2 hardening members: §12.4.2 audit tagging +
§12.4.3 capability allow-list are required v1 even when MCP is
disabled — so an operator flipping MCP on later doesn't need a
new release to get the hardening.

### §12.3  Interconnections ✅

| Direction | Other party | Wire | Notes |
|-----------|------------|------|-------|
| Inbound | AI agent | MCP stdio/socket | per the MCP spec |
| Outbound | mssh-ca | mTLS HTTPS (§3.3) | `/v1/admin/*` read-only subset |

The MCP server runs alongside or co-resident with mssh-ca. It
holds an admin mTLS cert (typically `auditor` role).

### §12.4  Implementation

Code: `packages/mssh-admin/src/mssh/mcp/`.

#### §12.4.1  Read-only diagnostics surface 🟡

MCP tools exposed in v1:
- `mssh.list_servers([group])`
- `mssh.list_users([username])`
- `mssh.list_admins()`
- `mssh.read_policy(username)`
- `mssh.list_intermediates()`
- `mssh.search_audit(filters)`
- `mssh.list_templates([scope])`
- `mssh.show_effective_template(server)`
- `mssh.status()` — health snapshot.

Each tool maps to one or more `/v1/admin/*` read-only calls.
Outputs are JSON, suitable for the agent to summarize / reason
about.

#### §12.4.2  Audit tagging 🚧 P3 — v1 ship blocker

Every call the MCP server makes to mssh-ca carries an
`Origin: mcp` header. mssh-ca records this in audit's `origin`
field (§4.3.7).

Listed as §13.9.2 hardening member, **required v1 even when MCP
is off** — the receiver logic in mssh-ca recognizes the header
regardless of whether MCP is currently enabled, so flipping it
on doesn't change the audit shape.

#### §12.4.3  Capability allow-list 🚧 P3 — v1 ship blocker

Explicit list of admin actions the MCP server is permitted to
proxy. Anything not in the list is refused at the MCP server
itself, **even if the underlying mTLS cert role would allow it**.

```yaml
mcp:
  enabled: false                          # off by default
  capability_allow_list:
    - server.list
    - user.list
    - admin.list
    - policy.read
    - intermediate.list
    - audit.read
    - template.list
    - template.show
  # NOT in allow-list (cannot be added in v1):
  #   - bypass-cert.mint            (per §12.2 (5))
  #   - intermediate.rotate         (audited destructive)
  #   - server.remove / user.remove (audited destructive)
  #   - cert.revoke                 (audited destructive)
```

The allow-list lives in `ca-config.yaml` (§14.3.2) but enforced
at the MCP server (refuse-and-log) **and** at mssh-ca (refuse
calls with `Origin: mcp` for non-allowed actions). Defense in
depth: a compromised MCP server can't issue actions the CA
refuses.

Listed as §13.9.2 hardening member, **required v1 even when MCP
is off**.

## §13  Cross-cutting subsystems

End-to-end stories that span multiple modules. The per-module §s
point here for the cross-cutting view.

### §13.1  Authz cache lifecycle ✅

Owners: msshd §5.3.5 + §5.3.6. CA §4.3.1 produces the input.

Full lifecycle of an authz cache entry:

```
       ┌──────────────────────────────────────────┐
       │  msshd boot                               │
       │  load <state_dir>/authz_cache.json        │
       │  (entries with not_after > now)           │
       └────────────┬──────────────────────────────┘
                    ▼
       ┌──────────────────────────────────────────┐
       │  incoming mssh connection                 │
       │  get(principal)                           │
       └────┬───────────────────────┬──────────────┘
            │ hit                   │ miss
            │                       ▼
            │           ┌─────────────────────────────┐
            │           │ POST /v1/authorize          │
            │           └────┬─────────────────┬──────┘
            │                │ granted         │ denied
            │                ▼                 ▼
            │     put(cert, source='ca')   invalidate_by_principal
            │     persist atomically       persist; close DENY
            │                │
            ▼                ▼
       use the cert; mint ephemeral OpenSSH cert; proxy session
                                │
                                ▼
                  on next /v1/authorize response from any
                  msshd: CRL drift triggers §13.3 sync;
                  if a serial in the cache is revoked,
                  invalidate_by_serial drops the entry.
```

**Source tag.** Every entry carries `source: 'ca' | 'bypass'`.
Lookup is source-agnostic — the tag is for diagnostic visibility
in `msshd-admin authz-cache show`.

**Persistence semantics.** Atomic write to
`<state_dir>/authz_cache.json` (mode 0600) on every put + every
invalidate. Survives restart. On boot, expired entries (by
`not_after`) are dropped.

**Cold-restart equivalence.** Eviction (§5.3.6) is operationally
equivalent to a cold start for the evicted principal: the next
connection re-calls the CA. If CA is down at that moment, that
principal is briefly denied — same as before any cache existed.

### §13.2  CA-bypass cert ✅

Owners: mssh-ca §4.3.6 (mint), mssh-admin §7.3.1 (UX), msshd
§5.3.7 (validate + inject), mssh §6.3.4 (carry on the wire).

End-to-end story:

```
T0 — operator mints, while CA is reachable:
    $ mssh-admin bypass-cert mint alice \
        --pubkey ~/.ssh/alice.pub \
        --valid-days 90 \
        --out alice-bypass.crt

    [CA: superuser-only call to POST /v1/admin/bypass-cert/mint;
     mint X.509 with OID_CA_BYPASS critical extension; signed
     by bypass-mint intermediate; return PEM + serial.]

T0+: operator stores alice-bypass.crt offline (USB key, safe).
     mssh-ca audit records the mint with the serial.

... time passes; CA becomes unreachable ...

T1 — operator wants emergency access:
    $ mssh --inject-bypass-cert alice-bypass.crt srv-acct

    [mssh: send JSON header carrying bypass_cert field.
     msshd: §5.3.7 5-step validation; put(principal, cert,
     source='bypass'); ack; close.]

T1+:
    $ mssh srv-acct -- whoami
    alice

    [mssh: normal connection. msshd: cache hit. No CA call.
     Session proceeds.]
```

**Why deliberately inconvenient.** Bypass certs live in safes,
not on disk. The two-step flow ensures the operator can't
accidentally use a bypass cert in routine work — they must
re-issue the inject step explicitly. Friction is the feature.

**Revocation.** A revoked bypass cert is invalidated by §13.3
same as a CA-grant cert (source-agnostic). The operator can
re-inject if still needed after the revocation reason has been
addressed (e.g. operator's primary access was restored, no need
for the bypass anymore).

### §13.3  CRL revocation channel ✅

Owners: mssh-ca §4.3.5, msshd §5.3.8.

Per-issuer, sequence-based, fleet-propagation. The §2.5 + §4.3.5
+ §5.3.8 mechanics produce this property: **any revocation issued
at the CA propagates to every msshd's authz cache by the
next-authorize hop from each msshd.**

End-to-end:

```
T0 — operator revokes:
    $ mssh-admin cert revoke <serial> --reason "key rotation"

    [CA: append-only CRL entry to <ca_dir>/crl/<issuer>.jsonl;
     seq increments.]

T0+ — fleet propagation:
    Every msshd, on its next /v1/authorize call (which happens
    on the next session from any user), receives current_crl_seqs
    in the response. If issuer X's current > last, msshd's CRL
    sync (§5.3.8) fetches the missing entries asynchronously.

    For each serial in the fetched entries:
        authz_cache.invalidate_by_serial(serial)
    persist last_crl_seqs[X].

T0+~bounded — quiescence:
    All cached entries with the revoked serial are gone fleet-wide
    by the time the slowest msshd hits its next authorize call.

    Strict-mode gate (§5.3.9): if a msshd has fallen >50 seqs behind
    on any issuer, it refuses cache hits and forces live CA calls
    until catch-up — prevents long-stale-cache from masking a fresh
    revocation.
```

**Source-agnostic.** A revoked bypass cert is dropped exactly
like a revoked CA-grant cert. Same policy for any cert; CA is
the oracle when reachable.

**Per-issuer independence.** A revocation against `bypass-mint`
doesn't appear in `user-mint`'s CRL or affect its `last_seq` —
the issuers are completely separate logs. This is what makes
"rotate one intermediate without flushing the others" tractable.

### §13.4  Cert auto-renewal ✅

Owners: mssh-ca §4.3.10, mssh-admin §7.3.3, systemd (§15.9).

Daily background job per host. Lifecycle:

```
00:00 + RandomizedDelaySec=30m
    systemd: cert-renew@msshd.timer fires
       └▶ cert-renew@msshd.service
             └▶ /usr/bin/mssh-admin cert renew \
                  --cert /etc/mssh/msshd-mtls-cert.pem \
                  --key /etc/mssh/msshd-mtls-key.pem \
                  --threshold-days 30 \
                  --revoke-old \
                  --on-renew "systemctl reload msshd"

    mssh-admin:
       1. read cert, compute days_until_expiry.
       2. if > 30: exit 0 silently.
       3. else: POST /v1/cert/renew with current cert.
       4. CA: validate caller cert chain + CRL; if in renew
          window (< 30d) and not past grace (now - not_after < 7d):
             mint replacement preserving CN/SAN/EKU/markers;
             return new cert+key.
       5. write atomically (temp + rename); chmod 0600 the key.
       6. invoke --on-renew CMD.
```

**Why this design instead of ACME.** ACME's HTTP-01 / DNS-01
challenges don't fit mssh's network-restricted CA. The cert
renewal endpoint reuses the existing mTLS auth — the cert IS
the credential, no extra handshake. ~2000 LOC of RFC 8555
compliance is replaced with ~620 LOC across CA + CLI + systemd.

### §13.5  Admin 2FA (passkey) flow ✅

Owners: mssh-ca §4.3.8, mssh-admin §7.3.2, mssh-passkey §8.

End-to-end:

```
T0 — policy:
    $ mssh-admin policy add --user alice --role admin \
        --require-2fa passkey --2fa-within-seconds 3600

    [CA: add policy; require_2fa=passkey on subsequent admin
     calls from alice's cert.]

T1 — admin calls a gated action:
    $ mssh-admin admin add bob --role admin

    [CA: receives /v1/admin/admin/add; sees alice's policy
     requires 2FA; passkey_check_2fa(alice):
       - cache miss (no fresh entry): start a ceremony.]

    [CA → broker: POST /broker/ceremony{kind=approve,
     user_handle=alice, outcome_url=..., ttl=300}]

    [CA → mssh-admin: 202 Accepted {ceremony_id,
     approval_url, poll_url, ttl_s}]

T1+ — operator approves:
    [CLI: prints approval_url + terminal QR.]
    Operator scans on phone, taps authenticator.
    [browser → broker /approve/<id>: WebAuthn assertion
     posted; broker validates against RP-side state.]
    [broker → CA outcome callback: status=approved, credential,
     aaguid.]
    [CA: AAGUID allowlist check; if ok, cache alice's 2FA
     window (1h); ceremony status → approved.]

T2 — CLI poll:
    [CLI: GET /v1/admin/passkey/ceremony/<id> until status==
     approved; then RETRY the original admin.add call.]
    [CA: receives the retry; passkey_check_2fa(alice) hits
     the fresh cache; proceed with admin.add.]
    [CA → CLI: 200 OK; admin record added.]
```

v1 gated actions (per `admin_2fa.protected_actions`):
`admin.add`, `admin.remove`, `user.remove`, `cert.revoke`.

### §13.6  External-tool RP flow ✅

Owners: mssh-ca §4.3.9, mssh-passkey §8, external tool.

End-to-end:

```
T0 — tool registration (one-time, mssh-admin):
    $ mssh-admin external-tool add my-tool \
        --outcome-url-prefix https://my-tool.example.com/cb/

    [CA: mint tool-mTLS cert via auth intermediate (or a
     dedicated external tier); record tool_id + prefix +
     aaguid_allowlist (inherit ca-global by default).
     Return cert + key for the tool to install.]

T1 — tool needs to challenge its user (Alice):
    [tool → CA: POST /v1/external/passkey/challenge
     {user_handle=alice, outcome_url=https://my-tool.example.com/cb/alice-1234}]
    [CA: validate outcome_url against tool's prefix; refuse if mismatch.
     Start ceremony via broker. Return ceremony_id + approval_url.]

T2 — Alice approves (browser hits broker; broker validates):
    [browser → broker /approve/<id>: WebAuthn assertion.]
    [broker → CA: outcome callback {status=approved,credential,aaguid}]
    [CA: validate aaguid against tool's allowlist (or CA-global).
     Two-hop callback: CA → tool's outcome_url with the result.]

T3 — tool acts on the outcome:
    [tool's outcome_url receives the POST; verifies the request
     came from the CA via mTLS; processes.]
```

**Cross-tool isolation.** Tool A's mTLS cert cannot read Tool B's
ceremonies. The CA matches the tool-id from the calling cert
against the ceremony's owning tool_id.

**outcome_url_prefix enforcement.** Tool A's outcome can only
go to a URL under its registered prefix. A compromised tool cert
cannot redirect outcomes to attacker-controlled URLs.

**AAGUID allowlist.** v1 inherits the CA-global allowlist; per-tool
override is post-v1 (§18.2).

### §13.7  Auxiliary certificate issuance 🟡

Owners: mssh-ca §4.3.11, mssh-admin §7.3.1.

CA-as-step-ca-parallel: mint leaves for non-mssh applications.
**The intermediate-pinning rule (§2.3) is what makes this safe** —
auxiliary leaves are signed by intermediates other than
`user-mint`, so they cannot be presented as authz certs.

v1 inventory:

| Leaf type | CLI | Intermediate | CRLDP |
|-----------|-----|--------------|-------|
| X.509 TLS server | `mssh-admin cert mint --type tls-server --cn X` | `host-mint` | ✅ |
| X.509 TLS client | `mssh-admin cert mint --type tls-client --cn X` | operator-chosen (typically `auth`) | ✅ |
| Code-signing (X.509) | `mssh-admin cert mint --type code-sign --cn X` | `auth` (today); `code-mint` planned per §15.17 | ✅ |
| OpenVPN client | `mssh-admin openvpn issue --cn X` | operator-chosen | ✅ |
| WireGuard peer | `mssh-admin wireguard peer-add --name X` | n/a (key material, not X.509) | n/a — dual-stack v0.4.0+, see §15.14 |
| PGP user key 🟡 | `mssh-admin pgp ...` | — | — |

The CA stores **only** the audit record of the mint. Private
keys are returned in the response and never persisted on the CA
side. Operators are responsible for safe key transport.

3rd-party-integration angle in §15.2.

### §13.8  Adoption journey (fallback → gated → enforce) ✅

The recommended operator path from "vanilla sshd" to "fully
CA-mediated SSH." Each step is reversible by a config flag.

```
                  CONFIDENCE
                       │
   day 0 ─▶ vanilla sshd on port 22
                       │
                       │  Step A: install msshd in FALLBACK mode
                       │           on port 22; move sshd to 22022.
                       │           Verify: connections still work
                       │           with operator's existing keys.
                       ▼
   week 1 ─▶ msshd fallback ─▶ sshd:22022
                       │
                       │  Step B: enroll users in mssh-ca; flip to
                       │           GATED mode. Now mTLS+CA at the
                       │           outer hop, operator's sshd at
                       │           the inner hop. Operators see
                       │           deny reasons in mssh-ca audit
                       │           BEFORE flipping enforce.
                       ▼
   month 1 ─▶ msshd gated ─▶ sshd:22022
                       │
                       │  Step C: migrate per-user policy to mssh-ca
                       │           policies. Flip to ENFORCE mode.
                       │           operator's sshd no longer in path.
                       ▼
   month 3 ─▶ msshd enforce (steady state)
```

**Reversibility.** At every step, flipping back to the previous
mode is a one-line config change. No state migration. This
property is why the modes are first-class instead of
implementation phases.

### §13.9  mssh-hardening (v1 deliverable) 🚧 P2 — v1 ship blocker

Aggregates the hardening work that must land before v1 release.
The hardened posture ships **regardless of which optional modules
are enabled**, so enabling an optional module later doesn't
require a follow-up release.

#### §13.9.1  Passkey-broker hardening v2 → §8.3.7

Injection / DoS / bogus-callback defenses on the CA receiver;
2FA fail-state mode (fail-closed default). Required v1 even when
the broker is not deployed.

#### §13.9.2  MCP attack-surface controls → §12.4.2 + §12.4.3

Audit tagging + capability allow-list. Required v1 even when
`mcp.enabled: false`, so the controls exist before any operator
flips the switch.

#### §13.9.3  Authz-cache eviction caps → §5.3.6

Already ✅; listed here so a future regression surfaces against
the hardening bar.

#### §13.9.4  Strict-mode CRL gate → §5.3.9

Already ✅; listed for the same reason.

#### §13.9.5  Bypass-cert validation surface → §5.3.7

Already ✅. Chain pin to `bypass_trust_root` + critical
`OID_CA_BYPASS` marker + validity window + mTLS-principal-match
must remain enforced.

#### §13.9.6  Audit log tamper-resistance posture 🚧 P2

v1 adds:
- **Hash chain or signed checkpoints.** Per-line:
  `hash(prev_hash || line) → next_hash`. Periodic checkpoint
  signed by `host-mint`. Truncation detected on next checkpoint
  read.
- **Documented retention + rotation policy.** Operator-configurable
  via `audit.rotation` in `ca-config.yaml`. Default: size-based,
  1024 MiB per file.
- **`mssh-admin audit verify`** — operator command that walks the
  hash chain + checks the signed checkpoints, reports any break.

#### §13.9.7  Default-deny on missing config 🚧 P2

Every config field that affects security posture has a
fail-closed default if absent. Examples:
- Unset `auth_trust_root` in `msshd.yaml` → refuse to start.
- Unset `bypass_trust_root` → bypass injection refuses.
- Unset `audit.path` in `ca-config.yaml` → refuse to start.
- Unset `ratelimits` block → refuse to start.

The verification pass (§0.5) confirms by exercising each field
absence individually.

#### §13.9.8  Cert OID + marker enforcement 🚧 P2

Every cert-validating site checks the §14.5 marker OIDs
explicitly (no "good chain, must be authorized" assumptions).
Cross-cuts §4.3.4 (mint), §5.3.7 (bypass injection), §5.3.11
(per-connection inner-sshd config validation), §11.3.4 (admin
web mTLS).

Per-validator audit:
- mssh-ca's authz mint refuses to produce a cert without
  `OID_AUTHZ_PRINCIPAL` populated.
- msshd's bypass validator refuses a cert without **critical**
  `OID_CA_BYPASS`.
- mssh-admin-web's mTLS validator refuses a cert without
  `OID_ADMIN_ROLE`.
- mssh-ca's admin handler validator refuses a cert chaining to
  `auth` but without `OID_ADMIN_ROLE` (prevents user-mTLS cert
  presentation as admin).
- **§13.9 mssh-hardening (v1 deliverable)** 🚧 **P2 — v1 ship
  blocker.** Aggregates the hardening work that must land before v1
  release. The hardened posture is shipped regardless of which
  optional modules a deployment turns on, so enabling an optional
  module later doesn't require a follow-up release. Members:
  - **§13.9.1 Passkey-broker hardening v2** → §8.3.7. Injection /
    DoS / bogus-callback defenses on the CA receiver; 2FA
    fail-state mode.
  - **§13.9.2 MCP attack-surface controls** → §12.4.2 (audit
    tagging) + §12.4.3 (capability allow-list). Required to land
    whether or not `mcp.enabled` is set, so the controls exist
    before any operator flips the switch.
  - **§13.9.3 Authz-cache eviction caps** → §5.3.6. Already ✅;
    listed here as a hardening member so a future regression
    surfaces against the hardening bar.
  - **§13.9.4 Strict-mode CRL gate** → §5.3.9. Already ✅;
    listed for the same reason.
  - **§13.9.5 Bypass-cert validation surface** → §5.3.7. Already
    ✅; listed for the same reason (chain pin + marker OID +
    validity + mTLS-principal match must remain enforced).
  - **§13.9.6 Audit log tamper-resistance posture** 🚧 — purpose:
    audit log is append-only JSON-Lines today (§4.3.7); v1 adds
    a documented retention + rotation policy and an integrity
    check (per-line hash chain or signed checkpoints).
  - **§13.9.7 Default deny on missing config** 🚧 — purpose:
    every config field that affects security posture has a
    fail-closed default if absent (e.g. unset `auth_trust_root`
    in msshd.yaml → refuse to start, not "trust everything").
    The verification pass (§0.5) confirms.
  - **§13.9.8 Cert OID + marker enforcement** 🚧 — purpose: every
    cert-validating site checks the §14.5 marker OIDs explicitly
    (no "good chain, must be authorized" assumptions). Cross-cuts
    §4.3.4, §5.3.7, §5.3.11.

## §14  Interfaces — canonical contracts ✅

Every interface a v1 deployment must implement bit-for-bit. **This
chapter is the source-of-truth for backward compatibility.** Anything
not in this chapter is implementation detail and may change without
notice; anything in this chapter is frozen and changes only via a
new design revision (§0).

### §14.1  REST API — mssh-ca ✅

All endpoints are mTLS-only; cert subject determines role. Common
response envelope on every JSON response:

```json
{
  "request_id": "<server-issued opaque id>",
  "ca_server_id": "<CA's enrolled server name>",
  "issued_at": "<ISO-8601 UTC>",
  "result": "granted" | "denied" | "ok" | "error",
  "protocol_version": "1.1",
  /* exactly one of: */
  "credentials":   { ... },           /* result=granted */
  "denied_reason": "...",              /* result=denied */
  "error":         { "code": ..., "message": ... }
}
```

HTTP status mapping:
- `200 OK` — `result: granted` (authorize) or `ok` (admin)
- `202 Accepted` — `result: pending` (2FA challenge)
- `400 Bad Request` — malformed input
- `401 Unauthorized` — mTLS failed or unknown cert subject
- `403 Forbidden` — authenticated, denied by policy or RBAC
- `404 Not Found` — unknown id (e.g. ceremony not in caller's
  scope)
- `429 Too Many Requests` — rate-limited
- `5xx` — CA internal error

#### §14.1.1  Public + mTLS-server endpoints

```
POST  /v1/authorize       — msshd → CA per-connection (§4.3.1)
GET   /v1/crl             — msshd → CA CRL sync (§5.3.8)
GET   /v1/crl.pem         — msshd-CA-equivalent / external reader,
                             PEM-format X.509 CRL per issuer
POST  /v1/cert/renew      — any holder of a CA-minted cert (§4.3.10)
```

**`POST /v1/authorize`** request body:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `protocol_version` | string | optional (default "1.0") | "1.1" enables `inner_sshd_config` in response |
| `request_id` | string | required | msshd-generated correlation id |
| `server_id` | string | optional | informational; CA looks up by mTLS subject |
| `identity` | object | required | `{type: "pubkey"\|"openssh-cert"\|"x509-cert", data: <base64>}` |
| `connection` | object | required | `{source_ip, source_port, timestamp}` |
| `requested_channels` | list of strings | optional | e.g. `["session"]` |
| `last_crl_seqs` | object | optional | `{<issuer_id>: <int>, ...}` |
| `inner_sshd_kind` | string | optional | "openssh" (v1 only) |
| `inner_sshd_version` | string | optional | e.g. "OpenSSH_9.6p1" |
| `msshd_version` | string | optional | calling msshd's package version |

**Granted response (200)**:

```json
{
  "result": "granted",
  "credentials": {
    "cert": "<base64 DER>",
    "cert_pem": "<PEM>",
    "serial": "deadbeef...",
    "not_after": "<ISO-8601>",
    "policy_summary": {
      "channels": ["session"],
      "source_bound": true,
      "server_bind": "srv-acct-01",
      "force_command": null,
      "environment": null
    }
  },
  "current_crl_seqs": {"user-mint:7f3c...": 45, ...},
  "inner_sshd_config": "<rendered sshd_config>",  // 1.1 only
  ...envelope...
}
```

**Denied response (403)** `denied_reason` enum:
`unknown_server`, `bad_request`, `clock_drift`,
`invalid_identity_cert`, `unknown_identity`, `policy_mismatch`,
`source_denied`, `time_window`.

**`GET /v1/crl?issuer=<id>&after=N&limit=K`**:

```json
{
  "result": "ok",
  "issuer_id": "user-mint:7f3c...",
  "current_seq": 45,
  "entries": [
    {"seq": 42, "revoked_at": "...", "serials": ["..."],
     "revoked_by": "admin:bob", "reason": "..."}
  ]
}
```

**`POST /v1/cert/renew`** request body:

```json
{"revoke_predecessor": false}    // optional; the cert IS the auth
```

Response 200:
```json
{
  "result": "ok",
  "status": "ok" | "too_early",
  "cert_pem": "<PEM>",            // if status=ok
  "key_pem": "<PEM>",             // if status=ok
  "serial": "...",
  "not_after": "<ISO-8601>",
  "predecessor_revoked": true | false,
  ...envelope...

```

`status: "too_early"` when `not_after - now > threshold_days`.

#### §14.3.1  msshd.yaml

**R-8 reconciliation (2026-05-22):** schema below mirrors the actual
`msshd/config.py` loader. Block names (`listen:` + `tls:` instead of

                                # (gated 🚧 P2 ship blocker — adds 'gated')

listen:
  external_address: 0.0.0.0
  external_port: 22
  interfaces: []                               # OPTIONAL bind list

# REQUIRED — common to gated + enforce
tls:
  server_cert:     /etc/mssh/msshd-server-cert.pem  # host-mint
  server_key:      /etc/mssh/msshd-server-key.pem   # mode 0600
  user_ca_pubkey:  /etc/mssh/user-ca-pubkey.pem     # accepted user CAs

users:
  allowed: ['*']                               # or explicit usernames

# REQUIRED — enforce only
inner:
  sshd_binary: /usr/sbin/sshd
  port_range: [10000, 65000]                   # tuple (lo, hi)
  mode: long-lived                             # OR per-connection
                                                # (note hyphen, not underscore)

# REQUIRED — fallback only
fallback:
  upstream_host: 127.0.0.1
  upstream_port: 22022

### §14.5  Custom X.509 OIDs ✅

mssh's IANA-style private arc: **`1.3.6.1.4.1.55555.1`**.

| OID | Name | Cert types | Format | Critical? |
|-----|------|-----------|--------|-----------|
| `1.3.6.1.4.1.55555.1.1` | `OID_SOURCE_BIND` | authz, bypass | UTF8String, CIDR | **yes** |
| `1.3.6.1.4.1.55555.1.2` | `OID_SERVER_BIND` | authz, bypass | UTF8String, server name or `*` | **yes** |
| `1.3.6.1.4.1.55555.1.3` | `OID_CHANNEL_POLICY` | authz, bypass | DER SEQUENCE OF UTF8String | **yes** |
| `1.3.6.1.4.1.55555.1.4` | `OID_FORCE_COMMAND` | authz, bypass | UTF8String | **yes when present** (R-1) |
| `1.3.6.1.4.1.55555.1.5` | `OID_ENVIRONMENT` | authz, bypass | DER SEQUENCE OF UTF8String (`K=V` form) | **yes when present** (R-1) |
| `1.3.6.1.4.1.55555.1.6` | `OID_MAX_SESSION` | authz, bypass | DER INTEGER (seconds) | no |
| `1.3.6.1.4.1.55555.1.7` | `OID_2FA_EVIDENCE` | authz, bypass | UTF8String (passkey ceremony id) | no |
| `1.3.6.1.4.1.55555.1.8` | `OID_CA_BYPASS` | bypass only | ASN.1 NULL (marker; presence = signal) | **yes** |

OIDs `.6` (`MAX_SESSION`) and `.7` (`2FA_EVIDENCE`) are policy-summary
information; not critical because a validator that doesn't recognize
them shouldn't reject the cert (msshd-side enforcement of session
duration is the authority).

OIDs `.4` (`FORCE_COMMAND`) and `.5` (`ENVIRONMENT`) are marked
**critical when present** by R-1: a validator that ignores them
would silently let the user out of a `ForceCommand` restriction —
exactly the failure the criticality flag is designed to prevent.
Consumer side (msshd + shim) lists them in `KNOWN_CRITICAL` so the
cert isn't rejected.

The arc was originally drafted (pre-2026-05-22) with different
names (`AUTHZ_PRINCIPAL`, `AUTHZ_VALID_FROM`, `AUTHZ_VALID_TO`,
`AUTHZ_CHANNELS`, `AUTHZ_SOURCE_CIDRS`, `AUTHZ_FORCE_COMMAND`,
`AUTHZ_ENVIRONMENT`) — those names were aspirational and never
implemented. R-1 reconciliation rewrote this table to match the
shipped arc.

OIDs `.9` and above are **reserved**; older drafts proposed
`USER_NAME`, `ADMIN_ROLE`, `INNER_SSHD_CONFIG_SIG`, `TOOL_ID` —
none implemented in v1. They are tracked in §18 as candidates for
future cert-bound RBAC + tool identity work.

Validators check the markers per §13.9.8.

### §14.7  Typed framing protocol v1.1 ✅

Inside the mssh ↔ msshd TLS tunnel, after the JSON header + ack
(§3.1), both sides switch to framed mode if negotiated.

**Wire layout per frame:**

```
struct frame {
    uint8  type;         // FRAME_TYPE_*
    uint8  flags;        // FRAME_FLAG_*  (currently 0)
    uint16 reserved;     // must be 0
    uint32 length;       // network byte order; payload length
    uint8  payload[length];
}
```

Fixed 8-byte header. No framing-level checksum (TLS handles
integrity).

**Frame types:**

```
mssh → msshd                       msshd → mssh
─────────────────────────────────  ─────────────────────────────────
  0x01  STDIN     stdin bytes        0x10  STDOUT   stdout bytes
  0x02  STDIN_EOF stdin half-close   0x11  STDERR   stderr bytes
  0x03  WINSIZE   resize 4 bytes BE  0x12  BANNER   pre-session banner UTF8
                                     0x13  EXIT     1-byte exit code
                                     0x14  SIGNAL   UTF8 signal name
                                     0x15  DENY     {"reason","detail"} JSON
  0x7F  CLOSE     graceful close     0x7F  CLOSE    graceful close
```

Reserved: `0x80+` for future extensions. Receivers must treat
unknown types as a protocol error and CLOSE.

**Frame semantics:**

| Frame | Payload | Notes |
|-------|---------|-------|
| STDIN / STDOUT / STDERR | opaque bytes | max 64 KiB; sender fragments larger writes |
| STDIN_EOF | empty | sender will write no more STDIN; receiver calls `chan.write_eof()` on inner SSH |
| WINSIZE | 4 bytes: u16 rows + u16 cols, BE | sent on local SIGWINCH if interactive |
| BANNER | UTF-8 text | sent at most once, before any STDOUT; mssh writes to its stderr |
| EXIT | 1 byte | remote exit code; sent immediately before CLOSE on graceful end |
| SIGNAL | UTF-8 signal name | sent instead of EXIT when killed by signal; mssh exits `128+N` |
| DENY | JSON `{"reason","detail"}` | sent at most once before any STDOUT on rejected sessions |
| CLOSE | empty | graceful shutdown; recipient closes TLS |

**Version negotiation:**

JSON header carries `supports_framing: true`. Ack carries
`framing: true` iff the server agrees. Mixed deployments (v1.0
client + v1.1 server, or vice versa) fall back to raw byte pump.

**Bypass-cert injection** (special non-session use):

JSON header carries `bypass_cert: "<base64 PEM>"` instead of a
session-RPC request. msshd validates per §5.3.7, acks via JSON
`{ok: true, bypass_injected: true}`, closes — no frames
exchanged.

### §14.8  Cert profile templates ✅

Each cert type's to-be-signed (TBS) content, in order they're
serialized:

#### Authz cert (mint via `user-mint`)

**R-1 + R-2 reconciliation (2026-05-22):** profile reflects shipped
code post-Phase-1 commits. R-2 added the X.509 hardening extensions
(`KeyUsage`, `ExtendedKeyUsage`, `SubjectAlternativeName`,
`SubjectKeyIdentifier`, `CRLDistributionPoints`) that the pre-Phase-1
draft promised; the consumer-side `KNOWN_CRITICAL` allowlist on msshd
+ shim was extended to accept the new critical extensions.

```
Subject:                CN=<subject_username>,O=mssh
NotBefore/NotAfter:     per policy (min of all matched)
Extensions:
  BasicConstraints        ca=False, path_length=None    (critical)
  KeyUsage                digitalSignature              (critical, R-2)
  ExtendedKeyUsage        id-kp-clientAuth              (critical, R-2)
  OID_SOURCE_BIND         <CIDR>                        (critical)
  OID_SERVER_BIND         <server name or '*'>          (critical)
  OID_CHANNEL_POLICY      <SEQUENCE OF UTF8String>      (critical)
  OID_FORCE_COMMAND       <UTF8String, if policy>       (critical, R-1)
  OID_ENVIRONMENT         <SEQUENCE OF "K=V" UTF8>      (critical, R-1)
  OID_MAX_SESSION         <INTEGER seconds>             (non-critical)
  OID_2FA_EVIDENCE        <UTF8 ceremony id>            (non-critical)
  SubjectAlternativeName  rfc822Name=<user>@mssh        (non-critical, R-2)
  SubjectKeyIdentifier    <leaf pubkey fp>              (non-critical, R-2)
  AuthorityKeyIdentifier  <user-mint pubkey>
  CRLDistributionPoints   <ca_url>/v1/crl.pem?issuer=user-mint:<fp16>
                                                        (non-critical, R-2; only when ca.crl_url configured)
```

Subject DN is intentionally minimal — the principal binding lives in
`OID_SOURCE_BIND` + `OID_SERVER_BIND` policy extensions, not the DN.
The SAN `rfc822Name=<user>@mssh` gives an alternative principal
binding for external X.509 validators that don't parse mssh's
custom OIDs.

**Why KeyUsage + EKU are critical:** without them, a leaf signed
by `user-mint` could be presented as e.g. a TLS server cert by an
attacker who captures the cert + key. The critical-when-present
posture means a validator that doesn't recognize the EKU restriction
must refuse the cert entirely — defense in depth for §2.3
intermediate pinning.

#### Bypass cert (mint via `bypass-mint`)
```
Subject:                CN=<subject_username>,O=mssh
NotBefore/NotAfter:     per mint args (days–months)
Extensions:
  BasicConstraints        ca=False                      (critical)
  KeyUsage                digitalSignature              (critical, R-2)
  ExtendedKeyUsage        id-kp-clientAuth              (critical, R-2)
  OID_SOURCE_BIND         <CIDR>                        (critical)
  OID_SERVER_BIND         <server name or '*'>          (critical)
  OID_CHANNEL_POLICY      <SEQUENCE OF UTF8>            (critical)
  OID_FORCE_COMMAND       <UTF8, if set>                (critical, R-1)
  OID_ENVIRONMENT         <SEQUENCE OF "K=V", if>       (critical, R-1)
  OID_MAX_SESSION         <INTEGER, if set>             (non-critical)
  OID_CA_BYPASS           <ASN.1 NULL>                  (CRITICAL, R-1)
  SubjectAlternativeName  rfc822Name=<user>@mssh        (non-critical, R-2)
  SubjectKeyIdentifier    <leaf pubkey fp>              (non-critical, R-2)
  AuthorityKeyIdentifier  <bypass-mint pubkey>
  CRLDistributionPoints   <ca_url>/v1/crl.pem?issuer=bypass-mint:<fp16>
                                                        (non-critical, R-2)
```

`OID_CA_BYPASS` is the marker that distinguishes a bypass cert from
a live-CA-grant authz cert. Format is **ASN.1 NULL** (`05 00`) —
its *presence* is the signal, not any value. R-1 fixed code from
emitting `UTF8String 'true'` to NULL.

Critical flag on `OID_CA_BYPASS` prevents a misconfigured validator
from accepting a bypass cert without recognizing what it is — same
posture as §13.9.8 enforcement.

#### mTLS server cert (`host-mint`)
```
Subject:                CN=<hostname>     (no Organization; R-2 will add O=mssh)
ExtendedKeyUsage:       id-kp-serverAuth
                        (R-2 will add id-kp-clientAuth for outbound msshd→CA mTLS)
```

#### mTLS user cert (`auth`)
```
Subject:                CN=<username>     (no Organization; R-2 will add O=mssh-users)
ExtendedKeyUsage:       id-kp-clientAuth
```

No mssh-specific OIDs — principal binding is by `CN` matched against
enrollment record. `OID_USER_NAME` was drafted as a cert-bound
binding but is not implemented in v1.

#### mTLS admin cert (`auth`)

**Deferred to Phase 2.** Today admin certs are minted the same way
as user certs (`issue_client_cert`); role is looked up by `CN` in
the enrollment record at request time, not carried on the cert.

The eventual admin-cert profile is a Phase-2 deliverable as part of
§13.9.8 (cert OID + marker enforcement extended to admin-RBAC by
cert) and would carry an `OID_ADMIN_ROLE` critical extension.

#### External-tool mTLS cert (`auth`)

**Deferred to Phase 2** (§15.5 external-tool RP work). Today the
external tool is identified by its cert's `CN` matched against the
`external_tools` enrollment record. The eventual profile would carry
an `OID_TOOL_ID` critical extension for stronger cert-bound binding.

#### Ephemeral OpenSSH user cert (msshd's local user-CA)

OpenSSH cert format, not X.509:
```
type:             ssh-ed25519-cert-v01@openssh.com (or ecdsa variant)
key id:           <msshd request_id>
valid principals: <principal>
valid_after:      now - 60
valid_before:     now + max_session_seconds (capped)
critical_options:
  force-command:  <from authz cert OID_FORCE_COMMAND, if set>
  source-address: <from OID_SOURCE_BIND, if set>
extensions:
  permit-pty
  permit-user-rc       <if policy allows>
  permit-X11-forwarding <if policy allows>
```

#### Auxiliary X.509 leaves (§13.7)

Profile per leaf type — TLS server uses `host-mint`, OpenVPN
client uses operator-chosen intermediate. None of them carry
`OID_AUTHZ_*` markers, so they cannot be presented as authz
certs (§2.3 + §13.9.8).

## §15  3rd-party integration ✅

The points at which **components can be replaced, shared, or
extended by external parties**. mssh is not a closed system; this
chapter is the canonical list of every extension point and the
contract each external integration must honor.

A v1 deployment can choose which integration points to use, but the
contracts here are frozen — a 3rd party who builds against §15
gets v1 backward-compatibility guarantees.

- **§15.1 Extension model — what's pluggable vs frozen** ✅ —
  *purpose:* the top-level taxonomy. Three categories:
  - **Replaceable components** (someone else's implementation can
    speak the same wire protocol): mssh-passkey broker (§15.4),
    mssh client (any TLS-1.3 + typed-framing speaker), inner sshd
    (any OpenSSH or compatible).
  - **Shared components** (mssh-ca lends its services to other
    apps): auxiliary cert issuance (§15.2), passkey RP for
    external tools (§15.5), External Intermediate CA tier (§15.3).
  - **Adapter components** (mssh borrows existing infra):
    OpenSSH AuthorizedKeysCommand path (§15.6), operator's
    existing sshd in fallback / gated modes (§15.7), apache2 as
    TLS terminator + reverse proxy (§15.8).

- **§15.2 CA as step-ca parallel (auxiliary cert issuance)** 🟡 —
  *purpose:* the CA mints leaves for non-mssh applications.
  Frozen contract: the API surface (§14.1.2 cert mint endpoints),
  the cert profiles (§14.8), the CRLDP placement on auxiliary
  certs. v1 inventory: X.509 generic TLS ✅, OpenVPN client ✅,
  WireGuard ✅, PGP 🚧 (post-v1). Why this is a 3rd-party
  integration point: anyone can deploy mssh-ca purely for one
  of these leaf types and never run msshd at all.

- **§15.3 External Intermediate CA tier** ✅ — *purpose:* `mssh-admin
  intermediate mint-external --name X --path-length N` mints a CA
  cert signed by the Root, hands the private key to the external
  entity (one-shot, OOB), and stores **only the public cert** on
  the mssh-ca side. The trust-store-exclusion rule (§2.3) ensures
  external-X-signed leaves cannot be presented as mssh authz
  certs — they validate to a different pin. Frozen contract:
  the path-length constraint, the cert profile, the
  trust-exclusion guarantee.

- **§15.4 Replaceable mssh-passkey broker** ✅ — *purpose:* a 3rd
  party can run their own ceremony broker as long as it speaks
  §3.6 (the broker wire protocol) and §14.6 (the ceremonies SQLite
  schema, or any storage that implements the same record shape).
  mssh-ca treats the broker URL as configuration; the broker is
  not trusted with key material. Frozen contract: the
  `/broker/ceremony[/<id>]` API surface, the callback delivery
  retry schedule, the mTLS-gating via `X-Client-CN`, and the
  per-ceremony binding rule (`ceremony.created_by ==
  caller-CN`, with cross-RP access returning 404).

- **§15.5 Passkey RP for external tools** ✅ — *purpose:* a 3rd-party
  app uses mssh-ca as its WebAuthn RP. The tool registers via
  `mssh-admin external-tool add`, gets a tool-mTLS cert, and calls
  `/v1/external/passkey/*` (§3.5, §14.1.3). Frozen contract:
  the endpoint set, the `outcome_url_prefix` enforcement,
  cross-tool isolation, AAGUID allowlist inheritance from
  CA-global (per-tool override is v2).

- **§15.6 OpenSSH AuthorizedKeysCommand integration (akc_shim)** ✅ —
  *purpose:* the operator can adopt mssh-ca-mediated authorization
  on an **unmodified OpenSSH** by pointing
  `AuthorizedKeysCommand` at `akc_shim`. The shim reads the user's
  pubkey, calls mssh-ca, returns the authorized-line. Frozen
  contract: the shim binary's stdin/stdout/exit-code shape, the
  envvars it reads (`SSH_RT_AUTH_*` legacy + `MSSH_*`).
  Composes with the optional `openssh-patches/` patches when the
  operator wants extra metadata visibility.

- **§15.7 Operator's existing sshd (fallback / gated modes)** ✅ —
  *purpose:* in fallback (§1.4.1) and gated (§1.4.2) modes, the
  authoritative auth machinery is the operator's existing
  `/etc/ssh/sshd_config`. msshd does not modify the operator's
  sshd — it proxies to it. Frozen contract: the upstream port
  + host that msshd connects to, the `passthrough` config block
  in `msshd.yaml`, the absence of any modification to the
  operator's filesystem outside `/etc/mssh/`, `/var/lib/mssh/`,
  `/var/log/mssh/`, `/run/mssh/`.

- **§15.8 apache2 as TLS terminator + reverse proxy** ✅ —
  *purpose:* mssh-passkey (§8.3.6) and mssh-admin-web (§11) both
  support apache2 as their public TLS terminator. The integration
  point is `front_end: apache` in their respective configs, plus
  the `X-Client-CN` mTLS-propagation header. Frozen contract:
  the header set apache forwards, the path layout, the auth-model
  (mTLS at apache, role check inside the backend).

- **§15.9 systemd integration** ✅ — *purpose:* every long-running
  component ships a systemd unit (in `systemd/`). The cert-renew
  timer template is the canonical example of "mssh extends a host
  with a daily background job." Frozen contract: the unit shapes,
  the `_msshd` system user, the `OnCalendar=daily` +
  `RandomizedDelaySec=30m` pattern for fleet-wide jobs.

- **§15.10 LXC / pyinfra integration for testing** 🟡 — *purpose:*
  the adhoc lab (§16.1) uses LXC containers driven by pyinfra
  inventories. 3rd parties can reuse the inventories to validate
  their own mssh deployments. Frozen contract:
  `python/tests/pyinfra-adhoc/` shape, the role-tagging
  convention. Phase A integration still in progress.

- **§15.11 What 3rd parties CANNOT replace in v1** ✅ —
  *purpose:* explicit list of non-extension-points so 3rd parties
  don't misinterpret the system as more open than it is.
  - The Root key + signing intermediates (Root + user-mint +
    bypass-mint + host-mint + auth are mssh-ca internals).
  - The msshd inner sshd's hermetic config (OpenSSH only; not
    pluggable to e.g. dropbear in v1).
  - The authz cache (msshd-internal; not exposed).
  - The typed framing protocol (frozen at v1.1; new frame types
    require a new design rev).

- **§15.12 PGP user key management** 🚧 P2 v1 — *purpose:* the CA
  as a step-ca parallel for PGP. Two modes:
  - **BYO mode:** operator imports an existing PGP pubkey for a
    user via `mssh-admin user pgp-key add`; mssh-ca stores the
    pubkey + fingerprint against the user record.
  - **CA-minted mode:** `mssh-admin pki mint-user --pgp` produces
    an OpenPGP keypair where the user's certify-key carries a
    third-party signature from a mssh-ca-managed signing key. The
    relationship is "mssh-ca attests this PGP key belongs to user
    X" — analogous to the §15.2 X.509 leaf semantics.
  - Frozen contract once landed: the OpenPGP format, the
    `mssh-admin user pgp-key {add,list,revoke}` surface, and the
    way the third-party signature is constructed (so 3rd-party
    tools that consume the PGP keys can verify).
  - Estimated: ~400 LOC + 15 tests. v1 P2.

- **§15.13 OpenVPN server-side registration** 🚧 P3 v1 — *purpose:*
  today the CA mints OpenVPN client certs via §13.7; v1 needs
  symmetric **server-side** support (server cert + a "register an
  OpenVPN server with the CA" workflow so the operator's VPN
  infrastructure is fully managed by mssh-ca). Small extension to
  existing OpenVPN minting. Estimated: ~80 LOC + 4 tests.

- **§15.14 WireGuard server-side registration** ✅ —
  *purpose:* symmetric with §15.13. Shipped pre-v0.4.0 as
  `POST /v1/admin/wireguard/server` + `GET /v1/admin/wireguard/server[/<name>]`
  + `DELETE` (R-4 added these to §14.1.2). **v0.4.0 adds dual-stack
  support**: `network` (v4) and `network_v6` (v6) are independently
  optional on server-init; at least one is required. The peer
  allocator picks the next free *host number* in the tunnel; when
  both families are present the same number is used in each (peer
  `.10` ⟷ `::a`). The v6-only path picks the smallest free integer
  ≥ 2 from the existing peer catalog — never enumerates the /64
  address space. The chosen IID scheme is implementation detail,
  not part of the wire contract — consumers parse the rendered
  address verbatim.

  Server-side `[Peer] AllowedIPs` lists the peer's host addresses
  (`…/32` + `…/128`) only; LAN routes are client-side and added by
  the upstream operator (e.g. totaldns). The peer-issue response
  carries `address_v6` as a structured field so callers don't have
  to regex it out of the rendered `client_config`.

- **§15.15 Webhook / event subscription** 🚧 v2 — *purpose:*
  operators subscribe to CA events (authz deny, cert revoke,
  intermediate rotate, etc.) for integration with SIEM /
  alerting. Not v1; captured here as a §-numbered placeholder so
  future work has a stable reference.

- **§15.16 HSM / external Root key custody** 🚧 v3 — *purpose:*
  Root key custody on hardware module or offline machine. v1
  stores Root on disk alongside intermediates. Migrating to
  HSM/PKCS#11 is a v3 deliverable; placeholder here keeps the
  long-term roadmap visible.

- **§15.17 Dedicated `code-mint` intermediate** 🚧 v1.x —
  *purpose:* today code-signing leaves (EKU=codeSigning, minted
  via `mssh-admin cert mint --type code-sign`) are signed by the
  `auth` intermediate (legacy `tls-ca-cert.pem` alias). Per §2.3
  intermediate-pinning, a code-signing leaf should chain to its
  own intermediate so it cannot be confused with admin-mTLS
  certs (which today share an issuer). Adds a fifth named
  intermediate `code-mint` to §2.2. Estimated: ~50 LOC + tests.

- **§15.18 CSR-based code-signing issuance** 🚧 v1.x —
  *purpose:* today `issue_codesign_cert` generates the keypair
  on the CA and returns the private key. For HSM/YubiKey-backed
  signing keys the private key must never leave the hardware
  module — the operator generates the keypair on-device and
  submits a CSR (PKCS#10 PEM); the CA verifies the CSR signature,
  enforces the cert profile, and returns just the signed
  certificate. Composes with §15.17. Estimated: ~80 LOC + tests.
  Update v0.5.0: the CSR infrastructure now ships in
  `mssh.ca.csr` (used by §15.19 external-use); a code-sign
  variant is a thin wrapper away. Marked 🟡 partial.

- **§15.19 External-use certificate kind** ✅ v0.5.0 —
  *purpose:* a generic, CSR-based leaf cert kind for uses
  outside mssh's own runtime (device identity per IEEE 802.1AR
  IDevID, ROM-burned firmware identity, BMC certs, IoT shadow
  certs, etc.). Operator-defined validity (per-kind via §15.23
  `cert_kinds:` section; default 7305 days / 20yr, cap 9125
  days / 25yr). Indefinite-expiry sentinel `notAfter =
  99991231235959Z` (RFC 5280 §4.1.2.5) when `never_expires:
  true` on the request body. **CSR-only** — the operator's
  hardware-bound key never touches the CA. Each leaf MUST pin
  (via §15.20 marker) to an external intermediate minted with
  `--profile <name>`. The cert's actual use case (device-mfg,
  bmc-id, etc.) is identified by operator-supplied custom OIDs
  from the §15.21 allowlist, not by a fixed kind name. Cert-kind
  marker `1.3.6.1.4.1.55555.3.9` (§15.23). REST:
  `POST /v1/admin/cert/external-use`. CLI: `mssh-admin cert
  mint --type external-use --cn N --csr F --issuer-intermediate I
  [--validity-days N | --never-expires] [--custom-oid OID=V] --out P`.

- **§15.20 `mint-external --profile <name>`** ✅ v0.5.0 —
  *purpose:* extend the existing §2.6 external-intermediate flow
  with operator-named profiles. Built-ins: `generic` (default —
  preserves v0.4.x behavior byte-identical) and `device-identity`
  (default validity 10950 days / 30yr; sets the §15.23 intermediate-
  purpose marker `1.3.6.1.4.1.55555.2.1` so external-use leaves
  can pin to it). Profile name is persisted to
  `<ca_dir>/external/<name>/profile.json` for diagnostics. Operator
  custom OIDs (§15.21) compose with the profile — operator can
  attach identifiers to the intermediate too.

- **§15.21 Operator-allowlist custom-OID injection** ✅ v0.5.0 —
  *purpose:* both intermediate-mint and external-use leaf-mint
  accept a `custom_oids: [{oid|name, value, critical?}]` list in
  the request body. CA validates each entry against an allowlist
  declared in ca-config.yaml's `custom_oids:` section (strict
  allowlist — empty allowlist = default-deny). Allowlist entry
  shape: `{oid, name, encoding, max_length?, description}` with
  encoding ∈ `{utf8, octet, integer, null, printable}`. **OID-arc
  reservation:** `1.3.6.1.4.1.55555.[1-4999].*` is mssh-reserved
  (hard-rejected from the allowlist regardless of YAML), and
  `1.3.6.1.4.1.55555.[5000-65535].*` is the mssh-assigned operator
  sub-arc (available without an IANA PEN registration). Operators
  with their own PEN may also use it. `CAConfig.validate()`
  refuses to start if any allowlisted OID overlaps the reserved
  range. The `mssh-admin init` writer emits a documented
  `custom_oids:` block with the reserved-arc reference table
  inline.

- **§15.22 Separate-Root option for external intermediates**
  ✅ v0.5.0 *(storage + mint flow)* — *purpose:* opt-in `new_root:
  true` (with optional `root_name: <name>`) on the external-
  intermediate mint flow. Creates a fresh Root + signs the new
  intermediate under it instead of the primary Root. Persisted
  under `<ca_dir>/roots/<root-name>/{cert,key}.pem`. `mssh.ca.roots`
  module loads all Roots at startup (primary + every non-primary).
  Downstream consumers add only the Roots they trust. v0.5.0
  scope intentionally limited to storage + load + mint flow;
  per-Root rotation, revocation, and admin-web visibility are
  v0.6+ follow-ups (in FEATURES-TODO).

- **§15.23 Cert-kind markers + per-kind validity policy**
  ✅ v0.5.0 — *purpose:* defense-in-depth + operator-configurable
  validity. **Markers:** every leaf the CA emits carries a
  non-critical NULL marker OID under `1.3.6.1.4.1.55555.3.*`
  identifying the cert's kind. The CA always emits these (no
  operator opt-out); marker is non-critical so legacy verifiers
  ignore it (RFC 5280 §4.2). Marker assignments:

  | OID | Kind |
  |-----|------|
  | `.3.1` | `authz-user` |
  | `.3.2` | `authz-bypass` |
  | `.3.3` | `server-tls` (legacy alias `tls-server`) |
  | `.3.4` | `admin-mtls` |
  | `.3.5` | `client-mtls` |
  | `.3.6` | `https-user` |
  | `.3.7` | `code-sign` |
  | `.3.8` | `openvpn` |
  | `.3.9` | `external-use` |

  Intermediate-purpose markers under `1.3.6.1.4.1.55555.2.*`:
  `.2.1` `OID_PURPOSE_EXTERNAL_USE_INTERMEDIATE` (set by §15.20
  non-`generic` profiles). Future profiles take subsequent slots.

  **Per-kind validity policy:** moved from hardcoded
  `_CERT_DEFAULT_VALIDITY` / `_CERT_MAX_VALIDITY` in admin.py
  into a `cert_kinds:` section of ca-config.yaml. Operator-set;
  baseline fallbacks in `config.py` preserve v0.4.x behavior
  byte-identical for configs without `cert_kinds:`. Per-kind
  lookup falls through `per_kind[<kind>]` → section-level
  defaults → built-in baseline. Bootstrap writer emits a
  documented section with sensible defaults per kind (VPN
  short, machine-identity very long, etc.).

  **Renewal-side kind-drift enforcement** is a v0.6+ follow-up
  (added to FEATURES-TODO); v0.5.0 emits markers on every mint
  and the renew path keeps inferring kind from EKU so existing
  v0.4.x certs continue to renew without disruption.

## §16  Operating envelopes ✅

How the system behaves at the edges.

### §16.1  Failure model — fail-closed ✅

Every error path denies. There is no "default allow."

| Failure | Behavior |
|---------|----------|
| CA unreachable (network, DNS, TCP) | deny — unless authz cache hit (§13.1) or bypass-cert path (§13.2) provides one |
| msshd's mTLS-to-CA fails (cert expired, chain invalid) | deny — operator must rotate via §13.4 |
| Outer mTLS handshake fails (client cert chain to wrong intermediate, expired, malformed) | deny at TLS layer; no audit record because TLS terminated before app sees the connection |
| `/v1/authorize` returns 403 | deny; DENY frame to client carries reason + detail |
| `/v1/authorize` returns 5xx | deny; DENY frame carries `ca_error` |
| Authz cert signature invalid | deny; treat as if CA returned error |
| Authz cert chain to wrong intermediate (e.g. cert signed by `host-mint` presented as authz) | deny — §13.9.8 marker enforcement |
| Strict-mode gate triggered (§5.3.9) | force live CA call; if CA unreachable, deny |
| Policy match returns no rule | deny — `policy_mismatch` |
| Source IP outside `source_cidrs` | deny — `source_denied` |
| Outside `time_window` | deny — `time_window` |
| 2FA required, ceremony fails / times out | deny |
| Inner sshd refuses the ephemeral cert (unexpected) | close the outer connection; log to msshd stderr; cache the authz entry as invalid for diagnostic visibility |
| Authz cache miss + CA unreachable + no bypass cert | deny |
| Required config field missing | refuse to start (§13.9.7) |

**Timing-side-channel posture** (§4.3.7): the time to "denied" must
not leak whether the user is enrolled vs. not. Constant-work denial
paths; detail goes to audit, not the wire.

### §16.2  Recovery paths ✅

Per failure class, the operator action that restores service:

| Scenario | Recovery |
|----------|----------|
| CA is down and a session is needed | present a pre-minted bypass cert via `mssh --inject-bypass-cert` (§13.2). Requires the operator to have stored a bypass cert offline ahead of time. |
| CA is down + per-connection inner-sshd mode | the emergency template renders locally (§5.3.12), giving a session with no per-session policy. Rate-limited. |
| CA is down + no bypass + no emergency | flip msshd to `mode: fallback` (§1.4.1) and route through the operator's existing sshd. Requires existing-sshd to still be running. |
| msshd's own mTLS cert expired (no daily renew job) | manual renew via `mssh-admin cert renew` from a workstation; copy to msshd; reload. |
| Intermediate compromised | `mssh-admin intermediate rotate <role> --force` (§2.5). Existing leaves under the old intermediate continue to validate until natural expiry (or admin-driven explicit revoke). |
| Root compromised | re-bootstrap the CA (rotate Root, rotate all intermediates, re-enroll everyone). v1 has no online recovery for Root compromise. (Post-v1: HSM + offline Root per §18.3.) |
| Audit log integrity break detected (§13.9.6) | the chain detects truncation; operator must investigate the gap. The signed checkpoints bound the window. |
| Lost mssh client cert | re-enroll via `mssh-admin user key add` then `mssh-admin user key remove <old-fingerprint>`. |
| Lost admin cert | another superuser must re-enroll. If no other superuser exists: re-bootstrap. |

### §16.3  Out of scope (deliberate non-features) ✅

| Non-feature | Why |
|-------------|-----|
| Password authentication | Passwords are guessable + phishable. SSH-keys + mTLS are baseline. |
| Per-server `/etc/ssh/authorized_keys` | All per-user authorization is a CA enrollment, not a server-side file edit. Eliminates "we forgot to push the change to one host." |
| Default mssh agent forwarding | Cert binds to a specific session; forwarding it cross-session is a policy choice that must be explicitly enabled in CA policy. |
| Long-lived authz credentials | Authz certs are minute-scale. Identity certs (user mTLS) are bounded by `/v1/cert/renew` policy. |
| In-band cert exchange (CSR over the wire) | Cert minting is an out-of-band step. The CA never accepts a CSR from a client; certs are minted at the CA and downloaded as part of enrollment. |
| Cross-CA federation | Multiple mssh CAs sharing a common Root is post-v1. |
| Certificate Transparency public log | mssh is a private-network CA; CT is for web-PKI hierarchies. Audit log is the equivalent. |
| Multi-key-per-principal cache | The per-principal cache key is the v1 shape. Multi-device support (per-principal × per-fingerprint) is post-v1; the per-principal cap (§5.3.6) is forward-compat plumbing. |
| Post-quantum KEX | Standard ed25519 + ECDH. PQ migration is an OpenSSH question mssh will inherit. |

## §17  Reference deployment + verification ✅

How a v1 deployment is provisioned, tested, and validated. **This
chapter also holds the verification artifacts that gate §0.5.**

### §17.1  Adhoc lab topology ✅

`python/setup_adhoc.sh` provisions a complete reference deployment
in LXC containers. The lab is the canonical "does this work
end-to-end" environment.

Containers (LXC, one role each):
```
ca         — mssh-ca (Flask + mTLS)
msshd      — msshd in enforce mode + hermetic OpenSSH inner sshd
admin      — operator workstation with mssh-admin + mssh client
alice      — end-user workstation with mssh client
[optional] passkey — mssh-passkey broker (via setup-adhoc-passkey.sh)
[optional] admin-web — apache2 + mssh-admin-web
[optional] debug — debug_sshd for diagnostics
```

Network layout: all containers on a shared bridge. CA is reachable
only from `msshd` and `admin` (verified by iptables/nftables rules
in the LXC profiles). `alice` reaches `msshd` directly; never
touches CA.

PKI bootstrap (`bootstrap_ca.sh` invoked by `setup_adhoc.sh`):
1. Mint Root + 4 intermediates (§2.2).
2. Mint CA's TLS server cert via `host-mint`.
3. Mint bootstrap admin cert via `auth` with `superuser` role.
4. Provision admin cert + key to `admin` container.
5. Use bootstrap admin to enroll `msshd` (server), `alice` (user),
   add alice's key, attach an access-everything policy.
6. Mint msshd's TLS server + mTLS client certs; provision.
7. Start msshd, mssh-ca services.
8. Smoke test: `mssh_as alice msshd whoami` returns `alice`.

Helpers (sourced via `python/adhoc-env.sh`):
- `mssh_as <user> <server> <cmd>` — runs mssh as that user.
- `flip_to_fallback` / `flip_to_gated` / `flip_to_enforce` —
  hot-flip the msshd mode and reload.
- `set_ca_unreachable` / `set_ca_reachable` — simulate CA
  partition for bypass-cert testing.

#### Known discrepancies — Phase 1 audit pass 2026-05-22

The Phase 1 audit pass found substantial drift between this design
and the shipped code. **Reconciliation plan: Path Z (hybrid)** —
Code→Design where design's interface is meaningfully better;
Design→Code where design is just renamed differently; DROP where
design over-spec'd unbuilt features.

Full per-discrepancy plan with commit-level breakdown lives in
[FEATURES-TODO.md](../FEATURES-TODO.md) under
"Reconciliation commit plan R-1 through R-10."

Audit headlines (each addressed by one or more R-* commits):

- **§14.5 OIDs (15 discrepancies, 9 HARD).** Arc `.1–.7` named
  differently in code; `.6`/`.7` undocumented; `.9–.12`
  documented but unimplemented. `OID_CA_BYPASS` wire-format
  differs (UTF8 vs NULL). → R-1.
- **§14.8 authz/bypass cert profiles.** Missing CRLDP, EKU, KU,
  SAN, SKI on authz cert. Bypass cert mint doesn't enforce
  `bypass-mint` intermediate. mTLS admin + external-tool profiles
  absent. → R-1 + R-2 + deferred to Phase 2 (admin + external-tool).
- **§14.1 REST endpoints (12 discrepancies).** Response envelope
  schema differs (`status` vs `result`, no `credentials` wrapper,
  no `request_id`/`ca_server_id`/`issued_at`). WireGuard paths,
  passkey paths renamed. `DELETE
  /v1/external/passkey/ceremony/<id>` missing in code.
  `intermediate.list` RBAC narrower than design. → R-3 + R-4.
- **§3.6 broker per-ceremony binding.** `views_broker.py` doesn't
  enforce `ceremony.created_by == X-Client-CN`; any allowlisted RP
  can read/cancel any ceremony. → R-5.
- **§14.6 audit.jsonl shape.** Key set entirely different
  (`timestamp` vs `ts`, `decision` vs `result`; flat actor vs
  nested admin). → R-6.
- **§14.6 + §14.4 on-disk state.** `authz_cache.json` uses
  `cert_der_b64` not `cert_pem`; missing `not_before` + `last_used_at`.
  `ceremonies.sqlite` table DDL barely resembles design. `enrollment.yaml`
  missing `intermediates:` section; users/policies/external-tools shape
  diverges. → R-7.
- **§14.3 config schemas.** All 6 schemas drift — block-name
  renames, undocumented fields, design-only fields not parsed,
  `mcp:` block + `audit.integrity` + `ratelimits` not read at all.
  → R-8 + R-9 + R-10.
- **§14.7 typed framing.** **MATCH** except bypass_cert wording
  (design says PEM, code uses DER-base64). Encoder/decoder is
  already in mssh-common as design suggested. Trivial doc fix. → R-1.
- **§13.9.7 default-deny.** `auth_trust_root` + `bypass_trust_root`
  not required in msshd validate(); `CAConfig.load` has no
  validation at all. → R-9 (pulled from Phase 3 into Phase 1 since
  schemas are settling).

Once R-1 through R-10 land, this section is replaced with a
reconciliation outcome log (one line per R-* commit + the new
state).

### §17.9  Reconciliation rules ✅

When the verification pass (§0.5) finds a mismatch:

| Finding | Action |
|---------|--------|
| §-ref in code, not in design | If the code-implemented behavior fits an existing §, update the comment. Otherwise the design needs a new §-ref — add it under §19+ RESERVED → renumber to the right place. **Either way, the design is no longer FROZEN until the rev is approved.** |
| § in design (✅), no code maps to it | Either the § was prematurely marked ✅ (downgrade to 🚧 in FEATURES-TODO + this doc), or the code is missing a §-ref comment (add it). |
| § in design (🚧), code maps to it | Update status to ✅; move row from FEATURES-TODO to FEATURES-COMPLETE. |
| Test exists, no §-ref | Update test docstring; treat as a bug per §0.3. |
| § exists, no tests | Add row to §17.8 + TESTS-TODO.md. The §'s status is 🟡 (implementation may be ✅ but verification is incomplete). |
| §-ref in code, § is RESERVED | Hard error. Code references a deleted §; needs to be updated to the replacement §. |
| Cert OID in `cert_minter.py`, not in §14.5 | Hard error. Add to §14.5 (post-FREEZE rev) or remove from code. |
| CLI flag in code, not in §14.2 | Hard error. Add to §14.2 (post-FREEZE rev) or remove from code. |
| REST endpoint in code, not in §14.1 | Hard error. Same as above. |

The "hard error" cases (last four rows) block release entirely
because they represent v1-contract drift between code and the
frozen interface chapter.
